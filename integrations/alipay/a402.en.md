# ACT 2.1 A402 Payment Access Protocol

[中文](a402.md) | English

> **Status: ACT 2.1 / Final / Non-normative extracted guide**
> Component: `PSD-PAY-A402`
> **Version baseline: 2026-08-11 (UTC+8).**
> **Translation status: Official English translation / Informative. If a translation discrepancy is found, the Chinese ACT 2.1 publication remains controlling until the translation is corrected in a subsequent repository release.**
> This guide extracts and explains `PSD-PAY-A402` from the [Payment Services Domain](../../docs/specification/payment-services.en.md). It adds no normative semantics. If it differs from that domain specification, the domain specification controls.

`PSD-PAY-A402` defines a general payment-access interaction based on HTTP `402 Payment Required` among a Buyer Agent, Seller Service, and payment service provider. The Buyer Agent accesses a paid resource or service. If no valid payment proof is available, the Seller Service returns a payment requirement. After the Buyer completes a payment that satisfies the current payment-scenario constraints, it accesses the resource again with payment proof. The seller delivers the resource and completes fulfillment confirmation only after successful validation.

`PSD-PAY-INS`, `PSD-PAY-DEL`, and `PSD-PAY-AUP` MAY use this component. A402 carries only payment-access interactions; it does not replace real-time confirmation, IAC constraints, cumulative limits, sub-account management, or other capabilities defined by the payment scenarios.

## 1. Participants and prerequisites

| Participant | Responsibility |
|---|---|
| Buyer Agent | Request a resource or service, parse the payment requirement, apply delegator-authorization checks, and obtain and submit payment proof |
| Seller Service | Provide a paid resource or service, create a payment bill, validate payment proof, and deliver the resource or fulfill the service; may be a merchant, platform, Seller Agent, or proxy interface |
| Payment service provider (PSP) | Accept payment under the selected method, create payment proof, provide proof-validation capability, and receive necessary fulfillment confirmation |
| Delegator | Confirm payment in real time for INS; predefine authorization boundaries through an IAC, sub-account, or equivalent mechanism for DEL/AUP |
| Merchant or resource provider | May be the same subject as the Seller Service, or may have resource access and payment handled by a Seller Service acting as its proxy |

Before entering this component:

- the Seller Service MUST consistently identify the billable resource, service, or order and create corresponding unique `resource_id` and `out_trade_no` values;
- the Buyer Agent MUST recognize HTTP 402, parse Base64URL-encoded Headers, select a supported `method_id`, and apply delegator-authorization rules;
- the participants MUST have determined an available payment method through `CID-PCA-NEG` or an equivalent mechanism.

## 2. Interaction flow

The following describes one payment-access interaction. It MAY repeat multiple times during a complete task lifecycle.

### 2.1 Request the paid resource

The Buyer Agent requests a resource, tool, API, digital content, or service from the Seller Service. The request MAY use `GET`, `POST`, or another HTTP method defined by the Seller Service.

The initial request normally does not carry `Payment-Proof`. If it does, the Seller Service MUST first validate its shape, validity period, transaction binding, and whether it has already been fulfilled.

### 2.2 Return the payment requirement

If the current request has no usable payment proof, or proof validation fails, the Seller Service MUST return HTTP `402 Payment Required` and include a Base64URL-encoded payment bill in the `Payment-Needed` Header.

```http
HTTP/1.1 402 Payment Required
Payment-Needed: <Base64URL-encoded payment bill>
Content-Type: application/json

{
  "error": "Payment Needed",
  "message": "Pay 0.01 CNY before accessing this resource",
  "resource_id": "RES_1739836600000_abc123"
}
```

The response body is for debugging, logging, and human-readable explanation only. The Buyer Agent MUST use the `Payment-Needed` Header as the machine-readable payment information.

### 2.3 Scenario validation and payment

After parsing `Payment-Needed`, the Buyer Agent MUST first apply the current scenario's prerequisite decision:

- `PSD-PAY-INS`: guide the delegator through real-time payment confirmation;
- `PSD-PAY-DEL`: validate IAC validity, amount, cumulative limit, merchant scope, and allowed payment methods;
- `PSD-PAY-AUP`: validate the `BOUNDED` IAC, task scope, cumulative budget, resource category, and Agent-dedicated sub-account state.

If any condition is not satisfied, the Buyer Agent MUST NOT continue to payment and MUST terminate the transaction, switch counterparties, or notify the delegator according to the configured policy.

After validation passes, the Buyer Agent MUST initiate payment with the PSP or method-defined endpoint according to the payment-method specification identified by `method_id`, then obtain a payment-authorization result credential. Payment tools, funds processing, IAC validation, and risk controls remain governed by the corresponding PSD scenario component and payment method; A402 does not redefine them.

### 2.4 Access again with payment proof

After successful payment, the Buyer Agent MUST make a new request for the original resource or service and include payment proof, PSP transaction number, Buyer session identifier, and other method-specific information in the `Payment-Proof` Header.

```http
GET /market/XXXX/trend HTTP/1.1
Payment-Proof: <Base64URL-encoded payment proof>
```

### 2.5 Seller validates payment proof

The Seller Service MUST parse `Payment-Proof` and call the PSP or a trusted validation service according to the payment-method specification identified by `method_id`. It MUST at least check:

- **Credential validity:** the signature, validity period, revocation state, and other validity properties of `payment_proof`;
- **Replay protection:** the credential has not already been fulfilled and cannot be reused for another resource access;
- **Consistency:** fields such as `trade_no` and `resource_id` match the current resource request.

If any check fails, the Seller Service MUST deny access to the paid resource and return machine-recognizable error semantics.

### 2.6 Deliver the resource and confirm fulfillment

After validation passes, the Seller Service MUST return the resource, begin service fulfillment, or confirm that the order may continue. It MAY return a machine-readable validation and fulfillment state in the `Payment-Validation` Header of the successful response.

```http
HTTP/1.1 200 OK
Payment-Validation: <Base64URL-encoded validation result>
Content-Type: application/json

{
  "status": "PAYMENT_VALIDATED",
  "trade_no": "2026040900828111317760000001xxxx",
  "resource_id": "RES_1739836600000_abc123",
  "resource": "XXXXXXXXXXXX"
}
```

After resource delivery or service fulfillment, the Seller Service MUST send fulfillment confirmation to the PSP according to the concrete payment-method specification. After the payment transaction completes, the PSP SHOULD asynchronously report an `act:payment:transaction-completed` attestation event for later audit, dispute handling, and task-billing review.

## 3. HTTP Headers and encoding

All three Header values MUST use **Base64URL-encoded UTF-8 JSON**.

| Header | Sender | Timing |
|---|---|---|
| `Payment-Needed` | Seller Service | Declares the payment requirement and core parameters in an HTTP 402 response |
| `Payment-Proof` | Buyer Agent | Carries the payment-authorization result credential when requesting the resource or service again |
| `Payment-Validation` | Seller Service | Returns the result after payment-proof validation; on success, the resource or service MAY be returned directly; on failure, an error code is returned |

## 4. Payment method `method_id`

`method_id` identifies a concrete payment method. Each method is maintained by an independent payment-method specification defining request construction, extension fields, signing algorithm, PSP validation logic, payment-authorization result credential, and error codes.

Before entering A402, the buyer and seller MAY negotiate and confirm `method_id`, `psp_id`, `endpoint`, and `method_schema_url` through `CID-PCA-NEG`, using them as input to later payment-request construction and execution.

ACT 2.1 does not further define `method_id` naming syntax, version expression, or registration. Implementations MUST NOT reverse-expand those matters into normative requirements of this version.

## 5. Payment payload structure

After decoding, all three Header payloads use a two-layer `protocol` plus `method` structure:

- `protocol`: baseline payload fields shared across payment methods;
- `method`: extension fields specific to the concrete payment method.

Payment-method extension fields MAY include account-identifier mapping keys, product information, signed-scope declarations, or other method-specific properties, but MUST NOT change the standard semantics of baseline fields. The corresponding payment-method specification independently defines and constrains those extensions.

### 5.1 Baseline payload fields

| Field | Type | Semantics |
|---|---|---|
| `method_id` | string | Identifier of the payment method used by the transaction |
| `out_trade_no` | string | External order number used for idempotency and transaction correlation |
| `amount` | string | Payment amount; SHOULD be a string to avoid floating-point precision loss |
| `currency` | string | Transaction currency; SHOULD use a standard currency code |
| `resource_id` | string | Resource identifier bound to payment, preventing credential substitution |
| `pay_before` | string | Payment deadline limiting the valid payment window and reducing replay risk |
| `seller_unique_id` | string | Unique identifier of the Seller Service |
| `buyer_unique_id` | string | Unique identifier of the Buyer Agent |
| `payment_proof` | string | Payment-authorization result credential |
| `trade_no` | string | PSP-generated transaction number or unique transaction identifier |
| `expires_at` | string | Expiration time of the payment-authorization result credential |
| `signer_id` | string | Identifier of the subject signing the message |
| `signature_content` | string | Signature value protecting message integrity and verifiable provenance |
| `signature_type` | string | Algorithm identifier needed to validate the message signature |

This table defines the shared field set and semantics. It does not independently define the presence of every field in each Header. The corresponding payment-method specification defines concrete distribution and constraints.

### 5.2 Payload examples

The following examples illustrate `protocol` and `method` layering. Fields under `method` belong only to the example payment method and are not general fields for every A402 implementation.

Decoded `Payment-Needed`:

```json
{
  "protocol": {
    "out_trade_no": "ORDER_1739836600000_abc123",
    "amount": "0.01",
    "currency": "CNY",
    "resource_id": "RES_1739836600000_abc123",
    "pay_before": "2026-03-25T12:00:00+08:00",
    "seller_signature": "YYYYxxxx=",
    "seller_sign_type": "RSA2",
    "seller_unique_id": "2088xxxxxxxx"
  },
  "method": {
    "seller_name": "Example merchant",
    "seller_id": "2088xxxxxxxx",
    "seller_app_id": "app_123456",
    "goods_name": "Example product",
    "seller_unique_id_key": "seller_id",
    "service_id": "xxxx_12344"
  }
}
```

Decoded `Payment-Proof`:

```json
{
  "protocol": {
    "payment_proof": "7cf8a6a93c924e13eaa4bf20c3a487f30d1fbdb759a1f229b4091b7d0158xxxx",
    "trade_no": "2026040900828111317760000001xxxx"
  },
  "method": {
    "client_session": "<method-specific-session>"
  }
}
```

The source example's `seller_signature` and `seller_sign_type` are not listed in the shared baseline-field table. An implementation therefore MUST NOT infer from the example alone that they are universally required fields for every payment method. Their applicability is defined by the concrete payment-method specification.

## 6. Transaction states

A concrete payment method MUST map its internal state to one of the following states before external output:

| State code | State name | Description | Allowed transition |
|---|---|---|---|
| `CREATE` | Created | Initial state | `WAIT_BUYER_PAY` |
| `WAIT_BUYER_PAY` | Waiting for buyer payment | Buyer has not completed payment | `WAIT_SELLER_FULFILLMENT`, `TRADE_CLOSED` |
| `WAIT_SELLER_FULFILLMENT` | Waiting for seller fulfillment | Buyer has paid; waiting for Seller Service fulfillment | `WAIT_BUYER_RECEIPT`, `TRADE_CLOSED` |
| `WAIT_BUYER_RECEIPT` | Waiting for buyer receipt | Seller has fulfilled; waiting for buyer confirmation | `TRADE_FINISHED`, `TRADE_CLOSED` |
| `TRADE_FINISHED` | Trade finished | Terminal state | None |
| `TRADE_CLOSED` | Trade closed | Terminal state for refund, cancellation, or another closure | None |

## 7. Error responses

Error responses SHOULD cover the following semantics. The Buyer Agent and Seller Service MAY use them to decide whether to retry, switch payment methods, change counterparties, or terminate the transaction.

| Semantic category | Description | Retry guidance |
|---|---|---|
| Signature-validation error | Signature fails or signature type is unsupported | SHOULD NOT retry directly; first inspect signature material, signer identifier, and algorithm configuration |
| Request-parameter error | Invalid parameter, amount, time format, or expired request | MAY retry after correction; obtain a new payment requirement after expiration |
| Protocol-validation error | Protocol missing or invalid, or payment-method specification mismatch | SHOULD NOT retry directly; first inspect payment-method configuration and protocol version |
| Agent-identity validation error | Buyer Agent or Seller Service identity validation fails | SHOULD NOT retry directly; first inspect identity documents, public keys, and bindings |
| Limit and asset validation error | Insufficient limit or balance, or asset-account validation failure | MAY retry after funding, adjusting limits, or selecting another payment tool |
| Authorization and risk-control error | User restricted, risk control triggered, or authorization boundary not met | SHOULD NOT retry immediately; wait for resolution or obtain new authorization |
| Transaction-state error | Transaction missing or current state does not permit continuation | SHOULD NOT retry directly; first query transaction state and apply idempotent handling |
| Refund error | Refund amount exceeds the limit or refund fails | Handle according to the reason; escalate to manual or compensation flow when necessary |
| Fulfillment-receipt error | Fulfillment fails or fulfillment-result receipt is abnormal | Decide whether to retry using the idempotency policy and fulfillment-state query |
| Payment-authorization result credential validation error | Credential empty, expired, missing, inactive, or inconsistent with subject, transaction, or resource | SHOULD NOT retry directly; obtain valid proof or initiate a new payment |
| System error | Internal exception or downstream failure | MAY retry a bounded number of times with exponential backoff, then alert or escalate |

## 8. Normative boundary and implementation artifacts

ACT 2.1 A402 does not define:

- exact required presence of baseline fields in the three Headers;
- `method_id` naming syntax, version expression, and registration governance;
- the original-request fingerprint algorithm or business idempotency key for non-safe HTTP methods;
- a concrete error envelope, error-code strings, or state-trigger event names;
- duplicate-fulfillment storage keys, delivery-idempotency keys, or record-retention periods.

The repository provides **Implementation Artifact / Non-normative** choices for these matters under [`code/schemas/a402/`](../../code/schemas/a402/README.md), for use by samples and tests. They MUST NOT be interpreted as additional ACT 2.1 normative requirements.
