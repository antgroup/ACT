# ACT 2.1 A402 支付接入协议

中文 | [English](a402.en.md)

> **状态：ACT 2.1 / Final / Non-normative extracted guide**
> 组件：`PSD-PAY-A402`
> **版本基线：2026-08-11（UTC+8）。**
> 本文为[支付服务域](../../docs/specification/payment-services.md)中 `PSD-PAY-A402` 的便捷提取与实现说明；不新增规范语义。若本文与支付服务域正文不一致，以支付服务域正文为准。

`PSD-PAY-A402` 定义买方智能体、卖方服务方与支付服务方之间基于 HTTP `402 Payment Required` 的通用支付接入交互：买方智能体访问付费资源或服务；卖方服务方在没有有效支付证明时返回支付诉求；买方完成符合当前支付场景约束的付款后，携带支付证明重新访问；卖方验证通过后交付资源并完成履约确认。

本组件可以被 `PSD-PAY-INS`、`PSD-PAY-DEL` 和 `PSD-PAY-AUP` 按需引用。A402 只承载支付接入交互，不替代各支付场景规定的实时确认、IAC 约束、累计额度边界或子账户管理等能力。

## 1. 参与方与前置条件

| 参与方 | 职责 |
|---|---|
| 买方智能体 | 请求资源或服务，解析支付诉求，执行委托人授权校验，取得并提交支付证明 |
| 卖方服务方 | 提供付费资源或服务，生成支付账单，验证支付证明并完成资源交付或服务履约；可以是商户、平台、卖方智能体或其代理接口 |
| 支付服务方（PSP） | 按具体支付方法受理支付、生成支付证明、提供支付证明验证能力并接收必要的履约确认 |
| 委托人 | 在 INS 场景中实时确认支付；在 DEL/AUP 场景中通过 IAC、子账户等方式预先定义授权边界 |
| 商户或资源提供方 | 可以与卖方服务方为同一主体，也可以由卖方服务方代理其资源访问和支付接入 |

进入本组件前，应满足：

- 卖方服务方能够稳定识别待收费的资源、服务或订单，并生成对应唯一的 `resource_id` 和 `out_trade_no`；
- 买方智能体能够识别 HTTP 402、解析 Base64URL 编码的 Header、选择支持的 `method_id` 并执行委托人授权规则校验；
- 参与方已经通过 `CID-PCA-NEG` 或等价机制确定可用支付方式。

## 2. 交互流程

以下流程描述一次支付接入；在完整任务周期内可以循环发生多次。

### 2.1 请求付费资源

买方智能体向卖方服务方请求资源、工具、API、数字内容或服务。请求可以使用 `GET`、`POST` 或卖方服务方定义的其他 HTTP 方法。

首次请求通常不携带 `Payment-Proof`。如果请求已经携带，卖方服务方应先验证其格式、有效期、交易绑定关系以及是否已被重复履约。

### 2.2 返回支付诉求

当前请求没有可用支付证明，或支付证明未通过验证时，卖方服务方应返回 HTTP `402 Payment Required`，并通过 `Payment-Needed` Header 携带 Base64URL 编码的支付账单。

```http
HTTP/1.1 402 Payment Required
Payment-Needed: <Base64URL 编码的支付账单>
Content-Type: application/json

{
  "error": "Payment Needed",
  "message": "请先支付 0.01 CNY 以访问资源",
  "resource_id": "RES_1739836600000_abc123"
}
```

响应体只用于调试、日志和人类可读提示。买方智能体用于机器处理的支付信息应以 `Payment-Needed` Header 为准。

### 2.3 场景校验与支付

买方智能体解析 `Payment-Needed` 后，应先执行当前场景的前置判断：

- `PSD-PAY-INS`：引导委托人实时确认支付；
- `PSD-PAY-DEL`：校验 IAC 有效性、金额、累计额度、商户范围和允许的支付方式；
- `PSD-PAY-AUP`：校验 `BOUNDED` IAC、任务范围、累计预算、资源类别和智能体专属子账户状态。

任一条件不满足时，买方智能体不应继续支付，并应按预设策略终止交易、切换交易对手或通知委托人。

校验通过后，买方智能体应依据 `method_id` 对应的支付方法规范，向 PSP 或该方法指定的端点发起支付并取得支付授权结果凭证。支付工具、资金处理、IAC 核验及风控仍由相应 PSD 场景组件和支付方法规定，A402 不重复定义。

### 2.4 携带支付证明重新访问

支付成功后，买方智能体应对原资源或服务发起新的请求，并通过 `Payment-Proof` Header 携带支付证明、PSP 交易流水号和买方会话标识等信息。

```http
GET /market/XXXX/trend HTTP/1.1
Payment-Proof: <Base64URL 编码的支付证明>
```

### 2.5 卖方验证支付证明

卖方服务方应解析 `Payment-Proof`，并依据 `method_id` 对应的支付方法规范调用 PSP 或受信验证服务，至少检查：

- **凭证有效性**：`payment_proof` 的签名、有效期、吊销状态等合法有效；
- **防重放性**：该凭证没有被重复履约，不能重复用于资源访问；
- **一致性**：凭证的 `trade_no`、`resource_id` 等字段与当前资源访问请求一致。

任一检查不通过时，卖方服务方应拒绝付费资源访问并返回机器可识别的错误语义。

### 2.6 交付资源与履约确认

验证通过后，卖方服务方应返回资源、启动服务履约或确认订单可以继续处理，并可在成功响应中通过 `Payment-Validation` Header 返回机器可读的验证及履约状态。

```http
HTTP/1.1 200 OK
Payment-Validation: <Base64URL 编码的验证结果>
Content-Type: application/json

{
  "status": "PAYMENT_VALIDATED",
  "trade_no": "2026040900828111317760000001xxxx",
  "resource_id": "RES_1739836600000_abc123",
  "resource": "XXXXXXXXXXXX"
}
```

卖方服务方完成资源交付或服务履约后，应按具体支付方法规范向 PSP 发起履约确认。支付交易完成后，PSP 宜异步上报 `act:payment:transaction-completed` 存证事件，用于后续审计、争议处理和任务账单回溯。

## 3. HTTP Header 与编码

三个 Header 的值均应采用 **Base64URL 编码的 UTF-8 JSON**。

| Header | 使用方 | 使用时机 |
|---|---|---|
| `Payment-Needed` | 卖方服务方 | HTTP 402 响应时声明支付诉求和核心参数 |
| `Payment-Proof` | 买方智能体 | 携带支付授权结果凭证重新请求资源或服务 |
| `Payment-Validation` | 卖方服务方 | 支付证明验证完成后返回结果；验证通过时可以直接返回资源或服务，验证失败时返回错误码 |

## 4. 支付方法 `method_id`

`method_id` 标识具体支付方法。每个支付方法由独立的支付方法规范维护，并定义该方法的请求构造、扩展字段、签名算法、PSP 核验逻辑、支付授权结果凭证和错误码。

进入 A402 前，买卖双方可以通过 `CID-PCA-NEG` 协商并确认 `method_id`、`psp_id`、`endpoint` 和 `method_schema_url`，作为后续支付请求构造与执行的输入。

ACT 2.1 未进一步规定 `method_id` 的命名语法、版本表达或注册机制；这些内容不得由实现反向扩展为本版本的规范要求。

## 5. 支付载荷结构

三个 Header 解码后的载荷均采用 `protocol` + `method` 两层结构：

- `protocol`：不同支付方法共享的基础载荷字段；
- `method`：具体支付方法特有的扩展字段。

支付方法扩展字段可以包含账户标识映射键、商品信息、签名覆盖范围声明或其他方法专属属性，但不得改变基础字段的标准语义。扩展字段的定义、约束和使用方式由相应支付方法规范独立说明。

### 5.1 基础载荷字段

| 字段 | 类型 | 语义 |
|---|---|---|
| `method_id` | string | 本次交易采用的支付方法标识 |
| `out_trade_no` | string | 外部订单号，用于幂等控制和交易关联 |
| `amount` | string | 支付金额；宜使用字符串避免浮点精度问题 |
| `currency` | string | 交易币种；宜采用标准货币代码 |
| `resource_id` | string | 与支付绑定的资源标识，用于防止凭证挪用 |
| `pay_before` | string | 支付截止时间，用于限制支付有效窗口并降低重放风险 |
| `seller_unique_id` | string | 卖方服务方唯一标识 |
| `buyer_unique_id` | string | 买方智能体唯一标识 |
| `payment_proof` | string | 支付授权结果凭证 |
| `trade_no` | string | PSP 生成的交易流水号或交易唯一标识 |
| `expires_at` | string | 支付授权结果凭证的有效截止时间 |
| `signer_id` | string | 生成报文签名的主体标识 |
| `signature_content` | string | 用于保证报文完整性和来源可验证性的签名值 |
| `signature_type` | string | 验证报文签名所需的算法标识 |

本表定义共享字段集合及语义，不单独规定每个字段在三个 Header 中的存在性；具体分布和约束由对应支付方法规范说明。

### 5.2 载荷示例

以下示例展示 `protocol` + `method` 的分层方式。`method` 中的字段只属于示例支付方法，不构成所有 A402 实现的通用字段。

`Payment-Needed` 解码后：

```json
{
  "protocol": {
    "out_trade_no": "ORDER_1739836600000_abc123",
    "amount": "0.01",
    "currency": "CNY",
    "resource_id": "RES_1739836600000_abc123",
    "pay_before": "2026-03-25T12:00:00+08:00",
    "seller_signature": "YYYYxxxx=",
    "seller_sign_type": "RSA2",
    "seller_unique_id": "2088xxxxxxxx"
  },
  "method": {
    "seller_name": "测试商家",
    "seller_id": "2088xxxxxxxx",
    "seller_app_id": "app_123456",
    "goods_name": "测试商品",
    "seller_unique_id_key": "seller_id",
    "service_id": "xxxx_12344"
  }
}
```

`Payment-Proof` 解码后：

```json
{
  "protocol": {
    "payment_proof": "7cf8a6a93c924e13eaa4bf20c3a487f30d1fbdb759a1f229b4091b7d0158xxxx",
    "trade_no": "2026040900828111317760000001xxxx"
  },
  "method": {
    "client_session": "<method-specific-session>"
  }
}
```

源文档示例中的 `seller_signature` 和 `seller_sign_type` 未列入共享基础字段表，因此不应仅依据示例将其解释为所有支付方法的通用必填字段；其适用性由具体支付方法规范说明。

## 6. 交易状态

具体支付方法的内部状态应映射到以下状态后再对外输出：

| 状态码 | 状态名 | 说明 | 可转入状态 |
|---|---|---|---|
| `CREATE` | 创建 | 初始状态 | `WAIT_BUYER_PAY` |
| `WAIT_BUYER_PAY` | 等待买家支付 | 买方尚未完成支付 | `WAIT_SELLER_FULFILLMENT`、`TRADE_CLOSED` |
| `WAIT_SELLER_FULFILLMENT` | 等待卖方履约 | 买方已支付，等待卖方服务方履约 | `WAIT_BUYER_RECEIPT`、`TRADE_CLOSED` |
| `WAIT_BUYER_RECEIPT` | 等待买家回执 | 卖方已履约，等待买方确认 | `TRADE_FINISHED`、`TRADE_CLOSED` |
| `TRADE_FINISHED` | 交易完成 | 终态 | 无 |
| `TRADE_CLOSED` | 交易关闭 | 退款、取消等关闭场景的终态 | 无 |

## 7. 错误响应

错误响应宜覆盖以下语义。买方智能体和卖方服务方可以据此决定是否重试、切换支付方式、更换交易对手或终止交易。

| 语义类别 | 说明 | 重试建议 |
|---|---|---|
| 签名校验错误 | 签名失败或签名类型不受支持 | 不宜直接重试；先检查签名材料、签名者标识和算法配置 |
| 请求参数错误 | 参数、金额或时间格式非法，或请求过期 | 修正后可以重试；过期时重新获取支付诉求 |
| 协议校验错误 | 协议不存在、无效或方法规范不匹配 | 不宜直接重试；先检查支付方法配置和协议版本 |
| 智能体身份校验错误 | 买方智能体或卖方服务方身份验证失败 | 不宜直接重试；先检查身份文档、公钥和绑定关系 |
| 额度与资产校验错误 | 额度或余额不足，或资产账户校验失败 | 补足余额、调整额度或更换支付工具后可以重试 |
| 限权与风控错误 | 用户被限权、触发风控或不满足授权边界 | 不宜立即重试；等待解除或重新取得授权 |
| 交易状态错误 | 交易不存在或当前状态不允许继续 | 不宜直接重试；先查询交易状态并做幂等处理 |
| 退款错误 | 退款金额超限或退款失败 | 依据原因处理；必要时转人工或进入补偿流程 |
| 履约回执错误 | 履约失败或履约结果回执异常 | 结合幂等策略和履约状态查询决定是否重试 |
| 支付授权结果凭证验证错误 | 凭证为空、过期、不存在、状态无效，或与主体、交易、资源不一致 | 不宜直接重试；重新获取有效凭证或重新发起支付 |
| 系统错误 | 系统内部异常或下游故障 | 可以指数退避有限次重试，超过阈值后告警或转人工 |

## 8. 规范边界与实现资产

ACT 2.1 A402 没有规定：

- 基础字段在三个 Header 中的精确必填性；
- `method_id` 的命名语法、版本表达和注册治理；
- 原请求指纹算法、非安全 HTTP 方法的业务幂等键；
- 具体错误对象封装、错误码字符串或状态触发事件名；
- 防重复履约存储键、交付幂等键和记录保存期限。

仓库在 [`code/schemas/a402/`](../../code/schemas/a402/README.md) 中提供这些方面的 **Implementation Artifact / Non-normative** 选择，供样例和测试使用。它们不得被解释为 ACT 2.1 新增规范要求。
