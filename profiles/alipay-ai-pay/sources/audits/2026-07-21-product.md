# Alipay AI Pay 公开产品事实核对（2026-07-21）

> 状态：Completed source audit / Non-normative  
> 核对日期：2026-07-21  
> 用途：验证双侧能力接入契约所引用的公开产品事实，不替代官网

## 1. 核对结论

公开官网能够支持“一条机器支付闭环、两侧能力”的产品定位：

- Agent 支付面向需要在用户授权范围内代用户下单和支付的智能体，并公开提供钱包、授权绑定和支付 Skill/CLI 路径。
- AI 按量付费是基于 HTTP 402 的 A2M 收款方案，使 API、数字内容或算力资源能够向访问它们的 Agent 发起收款。
- 官网公开时序把两侧连接为：资源请求、402 账单、用户授权支付、`Payment-Proof`、服务端验款、资源交付和履约回执。

因此，[双侧能力接入契约](../../capabilities/end-to-end-contract.md)的整体角色和时序成立。字段编码、金额单位、沙箱贯通和 API 错误细节仍存在需要产品确认或真实验证的项目。

## 5. 发现的差异和风险

| ID | 发现 | 影响 | 处理 |
|---|---|---|---|
| AUD-001 | `amount` 字段说明写“最小货币单位”，但示例为 `0.01` + `CNY` | 实现可能按分或元产生 100 倍偏差 | 保持 AP-001 `PRODUCT-REVIEW`；未确认前不写转换代码 |
| AUD-002 | `Payment-Needed` 明确写 Base64URL，`Payment-Proof` 示例文字写 Base64 | Binding 可能无法互操作 | 保持 AP-002 `PRODUCT-REVIEW`；用真实 Skill/CLI 输出验证 |
| AUD-003 | `client_session` 在接入指南中作为 Proof 内容和验款入参出现，但条件性未说明 | 不同 Agent 或调用方式可能缺参 | 保持 AP-003 `PRODUCT-REVIEW`；核对 API 文档和沙箱 |
| AUD-004 | 官网展示笔笔确认和限额免确认等模式，当前公开钱包指南主要说明开通绑定 | 授权级别与 Skill 实际能力可能被混淆 | July Preview 只声明逐笔确认；L2/L3 另行验证 |
| AUD-005 | 独立 API 文档本次无法通过公开抓取直接核对 | 错误映射可能过期或不完整 | `mappings/errors.md` 保持工作候选；发布前直接复核 API 文档 |
| AUD-006 | 官网提供 Sandbox，但尚未证明 Agent 钱包买方与 402 卖方能在同一笔沙箱交易贯通 | 端到端声明可能缺少完整证据 | 保持 `VALIDATION-PENDING`；下一步执行真实闭环 Spike |
| AUD-007 | 官网在 Proof 无效时建议重新支付，但重复付款前是否先查询原支付状态没有完整说明 | 自动恢复可能造成重复支付 | ACT/Profile 保持“先查询权威状态，不自动二次支付”的安全约束，待产品复核 |
| AUD-008 | npm `latest` 为 1.0.18，GitHub main 的 Skill metadata 声明 1.0.12；npm tarball 也不内嵌完整 Skill | 公开源码、安装器和实际运行 Skill 可能不是同一版本 | 验证时分别记录 npm、CLI、安装后 Skill 和源码提交，不使用模糊 `latest` 作为版本证据 |

## 6. 对接入契约的影响

本次核对后：

- 不修改双侧角色、端到端主时序和卖方验款不变量。
- 不把限额免确认或自主支付纳入 July Preview 的已验证范围。
- 不冻结 `amount` 的单位换算和 `Payment-Proof` 的编码算法。
- 不把独立 API 错误码或重试规则提升为已验证事实。
- 不允许仅凭官网存在 Sandbox 就声明端到端沙箱已经跑通。

下一轮需要真实运行官方 Skill/CLI，捕获脱敏的 402 输入、支付状态和 Proof 编码特征，并与卖方 Sandbox 的验款和履约结果组合成同一笔交易证据。
