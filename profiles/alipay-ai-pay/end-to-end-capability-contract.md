# Alipay AI Pay 双侧能力接入契约 v0.1

> 状态：Working Contract / Non-normative  
> 版本：`0.1`  
> 更新日期：2026-07-21  
> 适用范围：July Preview 中的 Agent 支付 + AI 按量付费 HTTP 402 闭环

## 1. 这份契约解决什么问题？

本文件在 ACT Core 修订期间固定支付宝 AI 付首期闭环的共同理解，使协议、产品 Profile、接入文档和沙箱验证围绕同一条交易链路推进。

它定义：

- 买方 Agent 支付能力与卖方机器支付能力的最小责任。
- 两侧需要交换和保存的交易语义。
- ADD、CID、PSD、TSD 上下文如何贯通。
- 哪些结果能够作为接入或兼容性证据。
- 哪些问题必须交给 ACT 协议修订决定。

它不定义正式 ACT Schema，不替代支付宝官网的开户、密钥、签名、API 或沙箱操作说明，也不能作为生产兼容性声明。

## 2. 一条闭环、两侧能力

| 能力侧 | 产品入口 | 首期公开载体 | 最小结果 |
|---|---|---|---|
| 买方 Agent 支付能力 | Agent 支付 | 支付宝官方 Wallet + Payment Skill/CLI | Agent 能理解机器付费要求，在有效授权下支付，并取得可提交给卖方的支付凭证 |
| 卖方机器支付能力 | AI 按量付费 | 支付宝官网 HTTP 402 方案 | 服务能机器可读地出账、验证支付凭证、防止重复履约、交付资源并确认履约 |

单独完成任意一侧，只能声明该侧能力已经接入。只有两侧在同一笔沙箱交易中完成互操作，才能声明端到端闭环通过。

## 3. 参与者与权威来源

| 参与者 | 主要责任 | 不是其责任 | 权威结果 |
|---|---|---|---|
| 用户 | 表达购买意图并在首期路径中确认支付 | 构造协议报文或验证 Proof | 用户授权或拒绝结果 |
| 买方 Agent | 保存原任务上下文，理解支付要求，调用官方支付能力，携带 Proof 重试 | 自行宣布支付成功或 Proof 有效 | Agent 任务状态；支付结果仍以支付宝为准 |
| 支付宝 Wallet/Payment Skill | 钱包状态、授权绑定、支付执行和结果查询 | 商品目录、卖方账单和业务履约 | 官方 Skill/CLI 返回的产品状态 |
| 卖方资源服务 | 生成账单、保存原始交易事实、验款、防重和交付 | 替用户决定是否支付或伪造支付结果 | 原账单、资源交付和幂等记录 |
| 支付宝产品 API | 支付凭证验证和履约确认 | 判断卖方业务资源是否正确交付 | 支付宝支付与产品接口结果 |
| ACT 实现 | 跨域语义、关联、状态恢复和证据边界 | 重写支付宝产品规则 | 声明范围内的 ACT/Profile 验证结果 |

## 4. 双侧最小能力契约

### 4.1 买方 Agent 支付能力

买方实现必须：

1. 使用支付宝官网公开的 Skill/CLI 获取支付能力，不以本地 Mock 代替。
2. 在支付前保留并展示可理解的收款方、金额、币种、商品或资源、订单和有效期。
3. 区分钱包不可用、需要授权、支付处理中、支付成功和支付失败。
4. 首期按照用户逐笔确认路径处理支付；未来委托或自主模式必须声明额外授权级别。
5. 保存原始资源请求，使支付完成后能够重试同一个请求。
6. 只携带官方能力返回的 `Payment-Proof`，不自行生成或修改 Proof。
7. 状态未知时查询权威支付结果，不自动发起第二笔支付。
8. 不在日志、测试证据或仓库中保存完整 Proof、绑定码、支付密码或可重放请求。

### 4.2 卖方机器支付能力

卖方实现必须：

1. 使用官网定义的 HTTP 402、`Payment-Needed`、签名规则和产品字段。
2. 在服务端生成金额、币种、商户订单、资源标识、收款方和支付截止时间。
3. 保存不可静默修改的原账单事实，用于后续一致性校验。
4. 将 `Payment-Proof` 视为不可信输入，并调用支付宝官方支付验证 API。
5. 在产品 API 成功后继续核对支付有效性、金额、订单、资源和交易号。
6. 原子地占用支付交易与资源的履约关系，阻止并发或重复交付。
7. 只在验证和本地一致性校验全部通过后交付资源。
8. 资源交付后调用支付宝官方履约确认 API，并对失败调用进行幂等重试。
9. 不把产品 API 的通用调用成功等同于业务验款成功。

## 5. 首期端到端顺序

| 序号 | 动作 | ACT 域 | 发起方 | 接收方 | 通过条件 |
|---|---|---|---|---|---|
| 1 | 用户请求收费资源 | ADD | 用户 | 买方 Agent | Agent 形成可追踪的购买意图 |
| 2 | 发起原始资源请求 | CID | 买方 Agent | 卖方服务 | 请求上下文可在支付后恢复 |
| 3 | 返回 402 和 `Payment-Needed` | CID → PSD | 卖方服务 | 买方 Agent | 账单可绑定资源、订单、金额、收款方和有效期 |
| 4 | 展示支付意图并确认 | ADD + CID | 买方 Agent | 用户 | 用户理解交易对象并明确接受或拒绝 |
| 5 | 调用官方支付能力 | PSD | 买方 Agent | 支付宝 | 使用已授权的钱包能力，不伪造结果 |
| 6 | 返回支付状态与 `Payment-Proof` | PSD | 支付宝 | 买方 Agent | Proof 来自官方能力；pending 与 success 可区分 |
| 7 | 携带 Proof 重试原请求 | CID → PSD | 买方 Agent | 卖方服务 | 资源请求与步骤 2 相同，Proof 未被修改 |
| 8 | 调用支付验证 API | PSD | 卖方服务 | 支付宝 | 使用官网接口验证 Proof 和交易 |
| 9 | 核对原账单并占用履约 | CID + PSD | 卖方服务 | 本地可信存储 | active、金额、订单、资源和防重全部通过 |
| 10 | 交付收费资源 | CID / 业务履约 | 卖方服务 | 买方 Agent | 只交付对应资源，重复请求不会重复产生副作用 |
| 11 | 确认履约 | PSD / 产品回调 | 卖方服务 | 支付宝 | 使用同一交易号幂等调用并保留结果 |
| 12 | 关联交易证据 | TSD | ACT 实现 | 证据存储/核验方 | 意图、订单、支付和履约证据可关联且来源明确 |

步骤 3 的 CID/PSD 边界、步骤 11 的 PSD/TSD 边界，以及 402 框架与 `PSD-PAY-INS` 的组合仍是协议待定项；本表只固定产品闭环所需的语义连续性。

## 6. 关联标识契约

| 标识 | 建议生成方 | 使用方 | 首期必须满足 | 状态 |
|---|---|---|---|---|
| `intent_id` | 买方 Agent / ADD 实现 | Agent、ACT 证据层 | 能关联用户意图、交易和最终结果；不要求写入支付宝产品报文 | `PROTOCOL-PENDING` |
| `delegation_id` | ADD 授权方 | Agent、支付执行、证据层 | 首期逐笔确认可不存在；L2/L3 必须可追踪授权范围和状态 | `FUTURE` / `PROTOCOL-PENDING` |
| `out_trade_no` | 卖方服务 | 买方账单、卖方存储、支付宝 API | 唯一定位原账单；重试不得静默换成另一笔订单 | `PUBLIC-FACT` |
| `resource_id` | 卖方服务 | 买方账单、卖方验证和履约 | 唯一定位准备交付的收费资源 | `PUBLIC-FACT` |
| `service_id` | 支付宝产品注册流程 | 账单和产品 API | 与官网登记的收费服务一致 | `PUBLIC-FACT` |
| `trade_no` | 支付宝 | 买方 Proof、卖方验证、履约确认 | 关联权威支付交易并作为防重关键输入 | `PUBLIC-FACT` |
| `payment_proof` | 支付宝支付能力 | 买方 Agent、卖方服务、验证 API | 不修改、不明文持久化、不作为未验证的交付依据 | `PUBLIC-FACT` |

最小关联链为：

```text
intent_id
  → out_trade_no + resource_id + service_id
  → trade_no + payment_proof
  → fulfillment evidence
```

ACT Core 是否要求这些标识进入统一消息或 TSD 事件，由协议修订决定。Alipay Profile 只负责产品字段映射和可验证关联方式。

## 7. 必须保持的闭环不变量

1. 没有用户授权或有效委托时，买方不得执行支付。
2. 没有支付宝权威结果时，Agent 不得宣称支付成功。
3. 没有官方验款和原账单一致性校验时，卖方不得交付收费资源。
4. 一笔支付不得造成多个非幂等资源交付。
5. 支付成功不等于资源已经交付；资源交付也不等于支付宝履约确认已经成功。
6. 支付重试、资源请求重试和履约确认重试是三个不同操作，必须分别保持幂等。
7. 过期账单不得被静默修改后继续使用；新金额或资源需要新的受控交易尝试。
8. 产品日志、API 返回和 ACT/TSD 事件必须标明来源，不能互相冒充。
9. 完整 Proof、私钥、绑定码和支付密码不得进入公开证据。

## 8. 状态与恢复契约

以下名称为工作语义，不是正式 ACT 枚举：

| 条件 | 责任侧 | 工作状态 | 合法下一步 | 禁止行为 |
|---|---|---|---|---|
| 钱包未开通或未绑定 | 买方 | `AUTHORIZATION_REQUIRED` | `AUTHORIZE_WALLET`、`ABORT` | 本地写死可用状态 |
| 用户拒绝授权或支付 | 买方 | `USER_DECLINED` | `ABORT` | 自动再次支付 |
| 账单已过期 | 双方 | `REQUIREMENT_EXPIRED` | `CREATE_NEW_REQUIREMENT`、`ABORT` | 修改旧账单有效期继续使用 |
| 支付处理中 | 买方 | `PAYMENT_PENDING` | `QUERY_PAYMENT_STATUS`、等待、`ABORT` | 立即创建第二笔支付 |
| 支付成功但暂未取得 Proof | 买方/支付宝 | `PROOF_PENDING` | 查询状态、`OBTAIN_NEW_PROOF` | 自行构造 Proof |
| Proof 无效或无法解析 | 卖方 | `PROOF_INVALID` | `DO_NOT_DELIVER`、取得正确 Proof、终止 | 先交付后补验 |
| 金额、订单或资源不一致 | 卖方 | `PROOF_MISMATCH` | `DO_NOT_DELIVER`、支持升级 | 接受错单、部分或超额支付 |
| 同一交易已经履约 | 卖方 | `PROOF_REPLAYED` | `RETURN_PRIOR_RESULT` 或拒绝 | 再次执行非幂等交付 |
| 验款 API 暂时失败 | 卖方 | `VERIFICATION_PENDING` | 用相同输入幂等重试 | 认为支付失败并要求重复付款 |
| 交付失败 | 卖方 | `DELIVERY_FAILED` | 幂等重试、补偿或升级 | 丢弃支付与交付证据 |
| 履约确认失败 | 卖方 | `FULFILLMENT_CONFIRMATION_PENDING` | 用同一交易号重试或查询 | 重复交付资源 |

完整候选错误映射见[Error mapping](error-mapping.md)，生命周期见[Lifecycle mapping](lifecycle-mapping.md)。

## 9. 分级验收声明

### 9.1 `AGENT_PAYMENT_CAPABLE`

只能证明买方侧能力，至少要求：

- 从公开来源安装官方 Skill/CLI。
- 实际完成钱包状态检查和必要授权。
- 支付前展示交易关键信息。
- 能区分 pending、success、failure。
- 能处理真实 402 账单并取得官方 Proof，或明确限定为收银台链接支付能力。
- 没有用 Mock 结果作为证据。

### 9.2 `MACHINE_PAYMENT_ACCEPTING`

只能证明卖方侧能力，至少要求：

- 真实返回官网格式的 402 和签名账单。
- 真实调用支付宝支付验证 API。
- 完成 active、金额、订单、资源和防重检查。
- 验证通过后交付资源。
- 调用履约确认 API 并保存可审计结果。
- 异常测试不会造成未付款交付或重复交付。

### 9.3 `ALIPAY_AI_PAY_END_TO_END_COMPATIBLE`

证明双侧互操作，至少要求：

- 前两级分别通过。
- 买方与卖方使用公开能力和官方沙箱完成同一笔交易。
- 从 `Payment-Needed` 到 `Payment-Proof`、验款、资源交付和履约确认全链路可追踪。
- 关联标识和证据来源满足本契约。
- 必测异常和重放用例通过。
- 声明明确绑定 ACT Core、Alipay Profile 和 Binding 版本。

这些声明名称是 July Preview 的工作标签，正式命名和合规规则需要通过治理评审。

## 10. 验证证据包

每次真实验证至少记录以下脱敏证据：

| 类别 | 必要内容 |
|---|---|
| 版本 | Agent Runtime、官方 Skill/CLI、ACT Core、Alipay Profile、Binding 和代码提交 |
| 环境 | 支付宝 Sandbox/测试环境标识和验证时间 |
| ADD | 脱敏意图标识、授权级别和用户确认结果 |
| CID | 脱敏资源、商户、金额、币种和商户订单摘要 |
| PSD | 402 结果、脱敏账单摘要、支付状态、脱敏交易号和验款结果 |
| 履约 | 资源交付结果、幂等记录和履约确认状态 |
| TSD/证据 | 事件时间、关联关系、证据来源和完整性说明 |
| 异常 | 用例、实际恢复动作和是否产生重复支付/交付 |

证据包不得包含私钥、访问令牌、绑定码、支付密码、完整 `Payment-Proof` 或可重放的完整请求。

## 11. 协议修订交接清单

以下问题由观岳牵头决定，本契约不预设答案：

1. 402 基础框架是否从 `PSD-PAY-AUP` 抽出，供 `PSD-PAY-INS`、`PSD-PAY-DEL` 和 `PSD-PAY-AUP` 共用。
2. `Payment-Needed` 是 `CID-CART-CFM` 的交易确认结果、它的载体，还是对独立确认对象的引用。
3. 双方支付能力声明和 `CID-PCA-NEG` 的最小字段及版本规则。
4. `Payment-Validation` 是否为独立消息，以及是否需要返回买方 Agent。
5. 支付回执、业务资源交付、支付宝履约确认和 TSD 事件的准确边界。
6. `intent_id`、`delegation_id`、`out_trade_no`、`resource_id`、`trade_no` 的 Core 最小关联规则。
7. `valid_next_actions` 的承载位置、执行者、重试间隔和最大次数。

每项结论形成后，应同时更新 ACT Core 候选、Alipay Profile 映射、端到端测试和迁移说明。

## 12. 下一步执行顺序

1. 按[官方资料表](official-sources.md)逐项核对本契约中的产品事实。
2. 用官方 Skill/CLI 与支付宝 Sandbox 执行[端到端 402 验证](../../docs/getting-started/end-to-end-402.md)。
3. 将实际输入输出、状态和异常与本契约比较，记录 `PRODUCT-REVIEW` 或 `VALIDATION-PENDING` 差异。
4. 将协议边界差异提交观岳决策，不在 Profile 中自行扩展 Core。
5. 决策完成后形成 Alipay AI Pay Profile 0.9 Preview 和相应一致性测试。
