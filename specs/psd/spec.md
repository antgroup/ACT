# 支付服务域（Payment Services Domain, PSD）

## 1 范围

支付服务域（Payment Services Domain，PSD）定义了智能体在完成购物车确认之后，向支付服务方发起支付的完整交互规范，覆盖支付请求的构造、授权核验、交易执行与结果状态管理等环节。

本协议在支付领域的设计思路如下：

- 兼容复用：本域规范最大限度兼容现有支付基础设施与行业惯例；
- 安全优先：敏感支付账户信息不直接暴露给智能体，通过支付标记化技术（Tokenization）进行隔离，同时通过意图授权凭证绑定用户授权边界，防范智能体越权支付；
- 可信可溯：结合信任服务域的可信存证能力实现端到端可审计。

**本域范围：**

- 定义面向智能体的支付交互流程；
- 定义 PSP 核验意图授权凭证有效性的核验要求；
- 定义 A2A 支付模式下交互流程及支付载荷结构；
- 定义支付方式绑定要求；
- 定义智能体专属子账户的管理规范；
- 定义支付完成后触发的关键事件类型，供信任服务域异步存证使用。

## 2 术语和定义

### 支付标记 Payment Token

支付标记服务方为智能体生成的、用于替代原始支付账户信息的令牌字符串。支付标记与委托人的原始支付账户存在安全绑定关系，智能体所接触和传递的始终是标记而非原始账号，从而将支付风险限定在可控范围内。

### 支付标记服务方 Payment Token Service Provider, PSTP

为敏感支付信息（如银行卡号、非银行支付账户信息等）提供标记化服务的机构或系统组件。其职责为生成、管理、验证支付标记（Payment Token），并限定标记的使用范围（如特定商户、特定智能体、金额上限等）。

### 支付服务方 Payment Service Provider，PSP

提供支付受理、指令路由与清算服务的机构（如收单方、第三方支付公司）。其职责为为智能体发起的支付请求提供接入接口，将支付指令路由至资金账户服务方或网络清算机构，并返回支付结果。

### 智能体专属子账户 Agent-Dedicated Sub-Account

为特定智能体（尤其是专属型智能体与执行自主委托任务的智能体）单独开立的资金子账户。该子账户与委托人主账户逻辑隔离，用于承载智能体自主支付的资金流转，并配套专属密钥实现签名授权。

## 3 本域协议组件列表

| 协议组件 | 组件描述 |
|---------|---------|
| `PSD-PMT-BND`：支付方式绑定 | 规范委托人通过支付标记化技术为智能体安全绑定支付方式及支付标记，实现敏感账号保护的流程。 |
| `PSD-AGT-SUB`：智能体专属子账户管理 | 规范为自主执行的智能体开立具有资金隔离能力的独立子账户，及其配套专属密钥的绑定与生命周期管理要求。 |
| `PSD-PAY-INS`：用户即时支付流程 | 定义在用户在场（Human-Present）场景下，实时完成商品和支付确认的交互流程。 |
| `PSD-PAY-DEL`：用户委托支付流程 | 规范委托人不在场情形下，智能体基于意图授权凭证，在用户设定的规则与限额内由智能体自主完成的支付流程。 |
| `PSD-PAY-A2A`：智能体A2A通用支付协议 | 规范智能体间基于 HTTP 402 语义扩展的通用支付骨架，涵盖"支付挑战-凭证传递-履约回执"的标准交互与状态流转机制。 |

## 4 协议典型场景与域内协议组件的关联

### 场景一：用户即时支付

**场景描述**：本场景适用于用户实时在场（Human-Present）且购买标的已在当次交互中明确的即时购买情形。用户在当次交互中实时完成支付授权，无需预先签发用户意图授权凭证。

涉及本域组件：

- `PSD-PMT-BND`：支付方式绑定，确保智能体持有有效的支付标记；
- `PSD-PAY-INS`：用户即时支付流程，处理实时确认到支付的完整消息流。

### 场景二：用户定向委托支付（平台型智能体）

**场景描述**：本场景适用于用户不在场（Human-Not-Present）且购买标的已在初始交互中明确（即定向委托）的情形。用户需预先签发定向委托类型的意图授权凭证，授权平台型智能体代为完成后续的商业发现与程序化支付。智能体在授权边界内程序化执行，无需用户实时介入。由于平台型智能体采用多租户共享架构（多用户共享同一智能体身份），为防范跨用户的越权与身份混淆，本场景的鉴权机制要求使用"平台智能体身份"与"具体委托人身份"的双重绑定组合来作为支付核验的基准。

涉及本域组件：

- `PSD-PMT-BND`：支付方式绑定，确保智能体持有有效的支付标记；
- `PSD-PAY-DEL`：用户委托支付流程；
- `PSD-AGT-SUB`：在平台型智能体场景下，可选通过智能体专属子账户进行支付。

### 场景三：用户定向委托支付（专属型智能体）

**场景描述**：本场景适用于用户不在场（Human-Not-Present）且购买标的已在初始交互中明确（即定向委托）的情形。用户需预先签发定向委托类型的意图授权凭证，授权其一对一绑定的专属型智能体代为完成后续的商业发现与程序化支付。与平台型智能体多租户共享的架构不同，专属型智能体与用户设备或账号强绑定，拥有独立且唯一的专属智能体身份。本场景的鉴权机制直接锚定该专属智能体身份进行核验，并支持通过为智能体设立独立子账户（预充值或限额授权），实现支付行为与用户主账户的资金风险隔离。

**涉及本域组件**：

- `PSD-PMT-BND`：支付方式绑定，确保智能体持有有效的支付标记；
- `PSD-PAY-DEL`：用户委托支付流程；
- `PSD-AGT-SUB`：在专属型智能体场景下，宜通过智能体专属子账户进行支付。

### 场景四：智能体自主委托支付

**场景描述**：本场景适用于用户不在场（Human-Not-Present）且购买标的由智能体在执行过程中自主决策（即自主委托）的情形。与场景二、三的定向委托不同，用户无需预先明确具体的购买标的，只需设定任务目标与行为边界（如总预算上限、品类范围、有效时间窗口）。在该授权边界内，智能体被赋予了高度的决策自主权，可自主完成子任务拆解、服务发现，并自主进行多次智能体对智能体（A2A）的交易，全程可无需用户逐笔介入确认。为确保资金隔离与机器间高频交易的安全，本场景要求买方智能体应使用专属独立子账户，与用户主账户进行资金风险隔离。

**涉及本域组件**：

- `PSD-PMT-BND`：支付方式绑定，确保智能体持有有效的支付标记；
- `PSD-PAY-A2A`：A2A 支付流程及支付载荷；
- `PSD-AGT-SUB`：在A2A支付场景下，应通过智能体专属子账户进行支付。

## 5 域内协议组件描述

### 5.1 PSD-PMT-BND：支付方式绑定

#### 概述

支付方式绑定（Payment Method Binding）规范了委托人向 PSP 完成智能体支付能力开通、并为智能体建立支付标记关联的操作流程。

#### 支付标记化技术的应用

在智能体支付场景中，智能体作为程序化执行主体，其本身不应直接持有或接触委托人的原始支付账户信息（如银行卡号、支付宝账号等）。为此，本协议采用支付标记化技术对原始账户信息进行隔离：

- PSP（或支付标记服务方）为委托人生成与其真实支付账户绑定的支付标记，并将该标记的使用范围严格限定至特定智能体标识；
- 智能体在发起支付时，仅使用该支付标记作为付款方账户凭证，PSP 负责在后台将标记逆向解析为真实账户进行资金扣划；
- 支付标记可配置金额上限、有效期及可用商户范围等风控参数，实现精细化风险隔离；
- 根据业务需求的不同，支付标记可分为一次性支付标记与长期支付标记，PSP 须根据标记类型的不同，施加相应的发行与管理要求。

#### 绑定操作流程

为智能体开通支付能力并绑定支付标记，宜由委托人主动触发。PSP 及智能体平台在实施该流程时，遵循以下流程：

**第一步：身份核验与意愿确认。** 委托人在智能体平台发起支付开通请求。智能体平台应将请求跳转至 PSP 侧完成委托人核身；PSP应对委托人身份及绑定意愿进行核验，核身方式包括但不限于生物识别、支付密码、动态验证码等。PSP应在核身界面中向委托人明确告知本次绑定的受托智能体身份标识及其授权范围，确保委托人的绑定意愿建立在知情基础上。

**第二步：生成与下发支付标记。** 认证完成后，PSP（或支付标记服务方）生成支付标记，并将该标记与以下信息进行绑定：委托人真实资金账户、受托智能体身份标识、标记有效期、金额上限（可选）。PSP 将该支付标记下发至智能体，智能体应保存支付标记，作为后续发起支付时对支付账户进行识别。

#### 绑定失败处理

若步骤一或步骤二中发生失败，PSP应向委托人的智能体返回失败原因，语义类别包括：身份核验失败、智能体身份未注册、账户额度超限等。

### 5.2 PSD-AGT-SUB：智能体专属子账户管理

#### 概述

智能体专属子账户（Agent-Dedicated Sub-Account）是为自主性较高的智能体提供账户级别的风险隔离机制，使委托人主账户不直接暴露于智能体自主执行的支付风险中。

#### 子账户的价值

相较于基于支付标记的绑定方式，智能体专属子账户具有以下价值：

- **资金预划拨**：委托人可预先将一定额度资金充值至子账户，智能体仅可在该子账户额度范围内完成支付，天然约束总额上限；
- **多轮自主支付支持**：自主委托场景下，智能体可能需要发起多笔支付，子账户支持连续多次扣款而无需每次均回调委托人授权；
- **独立账单与对账**：子账户产生独立的交易流水，便于委托人在任务结束后进行逐项核查与审计。

#### 专属密钥绑定

子账户应配套专属密钥，以实现子账户支付授权的有效验证。专属密钥支持非对称方案与对称方案两种模式，实现方可依据安全要求与部署条件选择适用方案。

- **密钥生成：** 子账户开立时，密钥应在安全执行环境中生成，且密钥材料不可导出。非对称方案下生成公私密钥对，对称方案下生成共享验证密钥；PSP 应将验证凭据（非对称方案下为公钥，对称方案下为验证密钥）与子账户标识完成绑定注册，作为后续验证的依据。
- **支付授权调用**：买方智能体构造支付载荷时，向安全组件传入密钥引用标识及待处理的载荷内容，由安全组件返回支付授权密文信息（非对称方案下为数字签名，对称方案下为消息认证码）。
- **密钥失效**：子账户冻结或注销时应联动触发密钥失效；密钥失效后PSP不应继续接受该子账户的支付请求。

> 注：上述密钥操作可基于外部安全服务组件实现，具体接口定义参见[安全接口声明](../appendix/security-interfaces.md)。

#### 子账户生命周期管理

支付服务方与智能体平台应支持完整的子账户生命周期管理机制：

- **开立与充值：** 子账户的开立须经委托人主动申请并通过 PSP 身份核验，PSP 应在开立时完成子账户、受托智能体身份标识与专属验证凭据的三方绑定注册。委托人可按需向子账户充值，充值操作应对委托人进行核身验证。PSP宜在子账户余额低于预设阈值时向委托人发出提醒。
- **冻结与解冻：** 当风控系统触发异常或委托人主动申请时，PSP应支持冻结子账户，并拒绝其后续一切支付请求。冻结状态可由委托人申请解除，解除时PSP应重新核验委托人身份。
- **注销：** 子账户注销为不可逆操作，可由委托人主动发起，或因智能体被注销而自动触发。注销时应联动触发专属密钥失效，子账户剩余余额应在规定时间内退还至委托人主账户。

### 5.3 PSD-PAY-INS：用户即时支付流程

#### 概述

用户即时支付（Instant Payment）流程适用于委托人实时在场、对本次购买行为进行即时确认并完成支付的场景。由于委托人全程参与了购买决策的闭环，无需预先签发意图授权凭证，委托人的实时收银台确认行为本身即构成本次支付的合法授权依据。

#### 流程步骤

**前置条件**：委托人已向买方智能体表达实时的购买意图，且买方智能体已在商业交互域完成规则前置检验与购物车确认（CID-CART-CFM），获取了待支付的商户侧订单信息。

**第一步：购物车确认与订单锁定**

买方智能体完成商业交互域的意图搜索与购物车确认流程，与商户锁定交易明细后，获取商户侧订单号及购物车信息（来自 `CID-CART-CFM`）。商户侧订单号是连接前端商业意图与后端资金清算的业务锚点。

**步骤二：构造并发送即时支付请求**

买方智能体向 PSP 发起即时支付请求，请求报文应包含以下核心要素：

- 本次请求的全局唯一标识，用于防重放；
- 来自 `CID-CART-CFM` 的商户侧订单号、购物车信息，供 PSP 验证支付内容与购物车的一致性；
- 前期绑定的支付标记；
- 本次支付金额及币种，应与购物车信息中总金额一致；
- 请求时间戳，用于 PSP 侧时效性验证；
- 买方智能体身份标识及对本次请求关键要素的签名。

**步骤三：PSP 基础校验**

PSP 在接收到支付请求后，应先完成以下基础校验，方可唤起收银台：

- 请求唯一标识防重放校验（验证该标识未被使用过）；
- 请求时间戳时效性校验；
- 买方智能体签名有效性校验；
- 支付标记有效性校验（标记未过期且与买方智能体身份绑定关系一致）。

上述任一校验未通过，PSP 应返回对应错误响应。错误响应覆盖以下语义类别：请求重复、请求已过期、签名验证失败、支付标记无效、标记与智能体身份不匹配。

**步骤四：唤起收银台与委托人即时确认**

PSP 向委托人唤起支付收银台或确认弹窗。收银台中应展示本次支付金额及币种、收款商户名称、支付方式，且展示内容应与支付请求中对应字段严格一致。

委托人通过核身方式完成即时确认后，PSP应记录本次确认所使用的核身方式及确认时间戳，作为本次支付的授权证据，供后续争议处理时核查。

**步骤五：PSP 执行扣款与状态回传**

PSP 将支付标记逆向解析为真实资金账户，完成资金扣划或额度冻结。PSP应将支付结果同步返回给买方智能体，返回内容应包含：PSP侧交易流水号、商户侧订单号（回传）、交易状态及交易时间戳。PSP应同步将支付结果通知商户。

**【存证】** 交易存证

支付交易完成后，PSP宜异步上报 `act:payment:transaction-completed` 存证事件，为后续潜在的争议解决提供支持。

### 5.4 PSD-PAY-DEL：用户委托支付流程

#### 概述

用户委托支付（Delegated Payment）流程适用于委托人已预先签发意图授权凭证，由买方智能体在无用户实时交互介入的情况下，依据授权边界代为执行程序化支付的场景。

#### 流程步骤

**前置条件**：委托人已预先完成意图确认并向买方智能体签发了有效的意图授权凭证（IAC），且买方智能体已在商业交互域完成规则前置检验与购物车确认（CID-CART-CFM），获取了待支付的商户侧订单信息。

**步骤一：智能体端规则自检**

买方智能体在构造委托支付请求前，应结合当前持有的意图授权凭证执行以下预检：

- IAC 处于有效状态（未过期、未吊销、未暂停）；
- 当前时间在 IAC 授权有效期范围内；
- 本次支付金额不超过 IAC 设定的单笔金额上限（若已设置）；
- 本次支付金额与本地缓存的累计扣款确认额之和不超过 IAC 设定的授权总额上限；
- 目标商户在 IAC 设定的允许商户范围内（若已设置）；
- 拟使用支付方式在 IAC 设定的允许支付方式列表中。

本地预检为买方智能体的前置过滤机制。若预检未通过，买方智能体不应继续发起支付。

> 注：本地缓存的累计扣款确认额应以 PSP返回的支付成功交易金额计算；首次支付前默认为零。

**步骤二：构造委托支付请求**

买方智能体向 PSP 发起委托支付请求，请求报文应包含以下核心要素：

- 本次请求的全局唯一标识，用于防重放；
- 来自 `CID-CART-CFM` 的商户侧订单号、购物车信息；
- 本次支付所依据的完整意图授权凭证及其委托标识；
- 本次支付金额及币种，应与购物车信息所覆盖的总金额一致；
- 支付工具凭据：未使用专属子账户时携带支付标记（对应委托人在 `PSD-PMT-BND` 中绑定的扣款账户）；使用专属子账户时携带子账户标识及其专属密钥支付授权密文信息；
- 请求时间戳；
- 买方智能体身份标识及对本次请求关键要素的签名，签名覆盖范围应包含请求唯一标识、委托标识、商户侧订单号、支付金额、币种及请求时间戳。

**步骤三：PSP 侧授权核验**

PSP 接收到委托支付请求后，应按以下顺序完成核验，任一项未通过则应拒绝本次请求并返回对应错误响应：

- **防重放校验**：验证请求唯一标识未被使用过。
- **买方智能体签名验证**：从买方智能体身份标识对应的身份文档中获取公钥，验证请求签名有效且覆盖范围完整。
- **IAC 有效性核验**：验证 IAC 签名有效；验证 IAC 未过期、未吊销、未暂停；验证 IAC 中受托智能体标识与请求中买方智能体身份标识一致；验证委托模式为本协议定义的有效枚举值。
- **金融层约束核验**：
  - 单笔金额校验：本次支付金额不超过 IAC 设定的单笔金额上限（若已设置）；
  - 累计额度校验：本次支付金额与 PSP 侧当前累计扣款确认额之和不超过 IAC 设定的授权总额上限；
  - 支付方式匹配：请求支付方式在 IAC 设定的允许支付方式列表中。
- **语义层约束核验**（可选执行）：
  - 商户白名单：收款商户标识在 IAC 设定的允许商户范围内。
  - 意图一致性比对：检查购物车信息如商品类目等与用户意图是否一致。
- 若使用专属子账户，PSP 还应对子账户专属密钥的支付授权密文信息进行有效性验证。

**步骤四：PSP 执行扣款与状态回传**

所有核验通过后，PSP 完成资金扣划或额度冻结（使用专属子账户时，资金直接从该子账户划扣或冻结）。PSP 应将支付结果同步返回买方智能体，返回内容应包含：

- PSP 生成的全局唯一交易流水号；
- 本次支付关联的委托标识与商户侧订单交易号（回传）；
- 交易状态及交易时间戳。

买方智能体在收到响应后，应以 PSP 返回的支付成功交易金额确认额更新本地缓存。PSP应同步将支付结果通知商户。

**【存证】**

支付交易完成后，PSP宜异步上报 `act:payment:transaction-completed` 存证事件，为后续潜在的争议解决提供支持。

#### 错误响应

委托支付流程中，PSP 返回的错误响应宜覆盖以下语义类别：

| 语义类别 | 说明 |
|---------|------|
| 请求重复 | 请求唯一标识已被使用，疑似重放攻击 |
| 请求已过期 | 请求时间戳超出有效窗口 |
| 智能体签名无效 | 买方智能体签名验证失败 |
| IAC 已过期 | IAC 有效期已到达 |
| IAC 已吊销 | IAC 已在吊销名单中 |
| IAC 已暂停 | IAC 处于暂停状态 |
| 智能体身份不匹配 | IAC 受托智能体标识与请求中智能体标识不一致 |
| 单笔金额超限 | 本次金额超出 IAC 单笔上限 |
| 累计金额超限 | 累计金额超出 IAC 授权总额上限 |
| 余额不足 | 账户或子账户余额不足 |
| 商户不在范围内 | 收款商户不在允许范围内（语义层核验，可降级为警告） |
| 金额与快照不一致 | 请求金额与购物车快照摘要覆盖的总金额不符 |

### 5.5 PSD-PAY-A2A：智能体对智能体支付

#### 概述

本组件规范了智能体对智能体（Agent-to-Agent）商业服务交互模式下的支付交互机制。协议采用"基础框架层 + 支付方法层"的双层分离设计，以兼顾通用互操作性与各类支付方法的差异性。

**基础框架层**（即本组件）定义与具体支付方法无关的通用 HTTP 交互骨架、凭证传递机制与履约回执机制；**支付方法层**由各具体支付方法（如数字钱包、银行卡等）的方法规范文档独立定义，包含该方法的具体字段、签名算法、账户体系、核验流程及错误码分配。

本组件适用于智能体自动化支付场景，支持多种支付基础设施（包括但不限于传统金融账户、数字钱包等）。具体支付方法通过注册唯一的 `network` 标识符进行区分，并由对应的方法规范文档独立维护。

在 A2A 支付流程中，智能体通过支付凭证（Payment Proof）机制实现支付状态的可验证性与可追溯性：PSP 在支付成功受理后返回的支付凭证，是买方智能体后续请求资源或服务的唯一合法凭据；卖方智能体收到携带支付凭证的资源请求后，须向 PSP 验证凭证有效性，方可放行资源访问并执行履约。

#### 交互流程

在进入实际支付交互前，买卖双方智能体**宜**基于 `CID-PCA-NEG` 支付能力协商组件，就支付方法、PSP 服务端点及扩展字段规范达成共识。随后的 A2A 支付交互流程步骤如下：

**步骤一：卖方智能体返回支付诉求**

买方智能体向卖方智能体请求商业服务时，若该服务需要付费，卖方智能体拦截请求并返回 **HTTP 402 Payment Required** 状态码，同时在 `PAYMENT-REQUIRED` 响应头中声明本次支付的核心参数，包括：

- 支付方法标识符（`network`）
- 支付金额及币种
- 收款账户标识
- 外部订单号（`out_trade_no`，由卖方智能体生成，用于幂等控制）
- 资源标识（`resource_id`，用于绑定支付与资源访问，防止凭证挪用）
- 卖方签名及签名类型
- 支付有效截止时间（`pay_before`，ISO 8601 格式，用于防范请求重放攻击并明确支付时间窗口）

卖方账户标识**应**与卖方智能体身份关联，确保资金结算与身份归属的一致性。

**步骤二：买方智能体提交支付**

买方智能体收到 HTTP 402 响应后，解析 `PAYMENT-REQUIRED` 中的支付参数，根据自有资产状况及授权凭证约束决定是否继续支付流程。

若决定继续，买方智能体构造支付请求并提交给 PSP（或经卖方智能体转发至 PSP）。支付请求中**应**包含买方身份凭据与支付授权密文，用于证明支付请求的真实性与完整性。支付请求的具体构造方式、凭据形式、签名算法及传输机制由支付方法规范定义。

**步骤三：PSP 核验与资金处理**

PSP 接收支付请求后，完成以下核验（具体核验逻辑的实现细节由支付方法规范定义）：

- 身份校验：验证买卖双方智能体身份标识的合法性；
- 签名校验：验证支付授权密文的有效性；
- 约束校验：验证授权凭证有效性及金融层约束（单笔限额、累计限额、支付方式匹配等）；
- 额度与风控校验：验证账户状态、余额及风控策略。

核验通过后，PSP 执行资金扣划或额度冻结，并向买方智能体返回支付凭证。支付凭证至少应包含：

- `payment_proof`：凭证哈希值，作为支付成功的唯一标识
- `trade_unique_no`：交易流水号
- `expires_at`：凭证有效截止时间（ISO 8601 格式）

支付凭证的返回方式及传输机制由支付方法规范定义。买方智能体**应**在后续请求资源或服务时携带该凭证。

**步骤四：买方智能体携带凭证访问资源**

买方智能体获得支付凭证后，再次向卖方智能体请求资源或服务时，**应**在请求头中携带 `PAYMENT-SIGNATURE` 头，其中包含支付凭证信息，证明指定订单或资源已完成合法支付。

卖方智能体收到请求后，**可**向 PSP 发起支付凭证验证，验证凭证的有效性（含有效性校验、防重复校验等，具体校验项由支付方法规范定义）。

**步骤五：卖方智能体返回资源**

验证通过后，卖方智能体通过 `PAYMENT-RESPONSE` 响应头向买方智能体返回验证结果及相应的付费资源或服务，结果中包含交易流水号、支付状态、金额、币种、处理时间及错误码等信息，并启动服务履约。

**步骤六：履约与归档**

服务履约、履约回执及归档确认的具体交互机制由支付方法规范定义，不在本基础框架层扩展 HTTP Header。

**【存证】** 交易存证

支付交易完成后，PSP **宜**异步上报 `act:payment:transaction-completed` 存证事件，为后续潜在的争议解决提供支持。

#### 支付方法（`network`）

本协议通过 `network` 字段标识具体的支付方法，每个支付方法对应独立的方法规范文档。

方法规范文档宜定义以下内容：

- 唯一的 `network` 标识符（小写字符串，大小写敏感）；
- 支付请求的构造方式、传输机制与 `PAYMENT-SIGNATURE` 中凭证的具体载荷格式；
- 该支付方法扩展字段的定义与约束；
- 买方身份凭据的形式与签名算法；
- PSP 核验逻辑的具体实现要求；
- 支付凭证的返回方式与传输机制；
- 履约回执与归档确认的交互机制；
- 方法专属的数字错误码段分配。

当前已注册的方法标识符：

| `network`标识符 | 对应规范文档 |
|----------------|------------|
| `example-wallet` | 《基于示例钱包的 A2A 支付》 |

#### HTTP Header 扩展规范

本协议基础框架层扩展以下三个 HTTP Header 字段。

| Header 名称 | 使用方 | 使用时机 |
|------------|--------|---------|
| `PAYMENT-REQUIRED` | 卖方智能体 | HTTP 402 响应 |
| `PAYMENT-SIGNATURE` | 买方智能体 | 买方携带凭证二次请求资源时 |
| `PAYMENT-RESPONSE` | 卖方智能体 | 支付凭证验证完成后 |

#### 支付载荷（Payload）结构

买方智能体构造并签名的支付载荷数据，在结构上划分为两个层次：

**基础载荷字段（Base Payload）**：所有 A2A 支付方法应具备的标准要素集合。

| 字段 | 类型 | 说明 |
|------|------|------|
| `network` | string | 支付方法标识符，由方法规范注册 |
| `out_trade_no` | string | 外部订单号，用于幂等控制 |
| `amount` | string | 支付金额（字符串格式，避免浮点精度问题） |
| `currency` | string | 交易币种（ISO 4217 三字母码） |
| `resource_id` | string | 资源标识，用于绑定支付与资源访问 |
| `pay_before` | string | 支付截止时间（ISO 8601 格式） |
| `seller_signature` | string | 卖方对支付诉求的数字签名 |
| `seller_sign_type` | string | 卖方签名算法类型 |
| `seller_unique_id` | string | 卖方唯一标识 |
| `buyer_unique_id` | string | 买方唯一标识 |

**支付方法扩展字段（Method Extension Fields）**：适应具体支付方法业务场景的附加属性层。买卖双方及 PSP 可在此层附加方法特定的业务参数（如账户标识映射键、商品信息、签名覆盖范围声明等）。扩展字段**不得**影响基础载荷字段的标准语义，具体字段由支付方法规范文档定义。

#### 交易状态

本协议定义以下通用交易状态，各支付方法的内部状态应映射到下列状态后对外输出：

| 状态码 | 状态名 | 说明 | 可转入状态 |
|--------|--------|------|-----------|
| `CREATE` | 创建 | 初始状态 | `WAIT_BUYER_PAY` |
| `WAIT_BUYER_PAY` | 等待买家支付 | 买方未完成支付 | `WAIT_SELLER_FULFILLMENT`、`TRADE_CLOSED` |
| `WAIT_SELLER_FULFILLMENT` | 等待卖家履约 | 买方已支付，等待卖方履约 | `WAIT_BUYER_RECEIPT`、`TRADE_CLOSED` |
| `WAIT_BUYER_RECEIPT` | 等待买家回执 | 卖方已履约，等待买方确认 | `TRADE_FINISHED`、`TRADE_CLOSED` |
| `TRADE_FINISHED` | 交易完成 | 终态 | 无 |
| `TRADE_CLOSED` | 交易关闭 | 终态（退款或取消） | 无 |

状态按业务流程单向流转，不可逆。任意非终态可通过退款或取消转入 `TRADE_CLOSED`。

#### 错误码

基础框架层定义以下错误语义类别，具体数字错误码由各方法规范按数字段自行分配：

| 错误类别 | 说明 |
|---------|------|
| 签名校验错误 | 签名验证失败、不支持的签名类型 |
| 请求参数错误 | 参数非法、金额格式错误、过期时间格式错误、请求已过期 |
| 协议校验错误 | 协议不存在或无效、合约不存在 |
| 智能体身份校验错误 | 智能体身份验证失败 |
| 额度与资产校验错误 | 额度不足、资产账户咨询失败 |
| 限权与风控错误 | 用户被限权、风控校验失败 |
| 交易状态错误 | 交易不存在、交易状态不合法 |
| 退款错误 | 退款金额超出限制、退款失败 |
| 履约回执错误 | 履约失败 |
| 支付凭证验证错误 | 凭证为空、凭证已过期或不存在、凭证状态无效、agent_id 不一致、trade_no 不一致 |
| 系统错误 | 系统内部异常 |
