## 1 范围

商业交互域（Commerce Interaction Domain，CID）定义了智能体与商户（含商户侧智能体）或其他智能体之间，围绕商品/服务发现、意图传递、内容协商、支付能力协商、购物车确认等环节所遵循的交互规范。

**本域范围：**

- 定义目前识别出的三类智能体商业交互模式；
- 定义智能体向一个或多个商户传递结构化意图的请求/响应规范；
- 定义商业服务交互中的支付能力协商流程；
- 定义购物车确认流程与规则前置检验要求；
- 定义商业交互过程中的关键事件类型，供信任服务域异步存证使用。

## 2 术语和定义

### 买方智能体 Buyer Agent

在商业交互链路中发起意图请求、完成比较决策与购物车确认的智能体。

### 商户 Merchant

提供实际商品或服务，接收交易请求并承担最终订单履约责任的商业实体。

### 卖方智能体 Merchant Agent / Seller Agent

代表商户或服务提供方参与商业交互的智能体实体，具有独立的智能体身份标识，可在授权范围内自主完成意图接收、商品或服务协商及交易确认等行为。

### 支付能力声明 Payment Capability Declaration

商户或卖方智能体对外公开发布的、声明本方所支持的支付方式及对应服务信息的结构化文档，供买方智能体在发起支付前进行支付能力发现与兼容性匹配。

### 支付能力协商 Payment Capability Negotiation

买方智能体与商户或者卖方智能体在发起支付前完成的支付方式匹配与参数对齐过程。

### 规则自检 Rule Self-Check

买方智能体在提交购物车确认前，依据当前有效意图授权凭证中的约束字段，对本次购买行为进行合规性自动校验的机制。所有检查项通过后，方可提交购物车确认并进入支付流程。

## 3 本域协议组件列表

| 协议组件 | 组件描述 |
|---------|---------|
| `CID-MER-CAT`：商品目录接口 | 规范商户向智能体开放结构化商品或服务目录的接入要求。 |
| `CID-INT-XFR`：意图上下文传递 | 规范买方智能体向商户或电商平台传递多维意图上下文，以换取精准候选推荐的请求与动态路由机制。 |
| `CID-CART-CFM`：购物车确认 | 规范买卖双方确认最终商品清单、金额，并将交易状态锁定准备进入支付阶段的交互过程。 |
| `CID-PCA-NEG`：支付能力协商 | 规定买卖双方智能体在交易前相互声明并匹配可用支付方式及 PSP 服务端点的握手过程。 |

## 4 不同商业交互模式与域内协议组件的关联

### 概述

实现方可依据以下条件选择适用的商业交互模式：

| 判断条件 | 推荐模式 |
|---------|---------|
| 商户已开放结构化商品目录接口，买方智能体自主完成商品筛选与决策 | 模式一：商品目录开放模式 |
| 商户支持意图传递接口，由商户侧完成商品筛选与推荐后返回候选结果 | 模式二：意图上下文传递模式 |
| 交易对手方为卖方智能体，双方需进行智能体对智能体的商业协商与支付能力匹配 | 模式三：A2A 商业服务交互 |

> 注：在实际系统的工程落地中，同一买方智能体可根据不同的商业场景、商品特性及交易对手方的技术能力，动态切换或在不同阶段组合使用不同的交互模式。

### 模式一：商品目录开放模式

**模式描述**：商户通过标准化 API 向智能体开放结构化商品目录，智能体直接读取商品信息完成发现与购买决策。

**涉及本域组件**：

- `CID-MER-CAT`：买方智能体通过该组件获取商户的商品目录最新情况；
- `CID-CART-CFM`：买方智能体在提交购物车前执行规则自检，通过后向商户/电商平台下单确认。

### 模式二：意图上下文传递模式

**模式描述**：买方智能体将委托人的结构化意图传递给一个或多个商户/电商平台，由商户/电商平台完成商品筛选与候选推荐，再由买方智能体完成比较决策与购物车确认。

**涉及本域组件**：

- `CID-INT-XFR`：买方智能体构造并发送意图请求，接收并汇总商户/电商平台返回的候选商品列表；
- `CID-CART-CFM`：买方智能体在提交购物车前执行规则自检，通过后向商户/电商平台下单确认。

### 模式三：A2A 商业服务交互

**模式描述**：买方智能体与卖方智能体之间，围绕商业服务的发现、协商与交易完成智能体对智能体交互，过程中可能会通过智能体服务市场来发现提供所需服务的卖方智能体。该模式中，本协议将在行业中现有通信层协议（如 Google A2A、ANP 等）的基础上，扩展定义了支付能力协商规范。

**涉及本域组件**：

- `CID-PCA-NEG`：买方智能体与卖方智能体在发起支付前完成支付方式与 PSP 的匹配；
- `CID-CART-CFM`：买方智能体确认提交支付前执行规则自检，通过后基于 A2A 支付（`PSD-PAY-AUP`）向卖方智能体提交支付。

## 5 域内协议组件描述

### 5.1 CID-MER-CAT：商品目录接口

商品目录接口（Catalog Interface）是商户向智能体开放结构化商品或服务目录的接入规范，支持智能体通过机器可读的方式完成商品发现与信息获取。

本协议当前版本不展开制定商品目录接口规范，鼓励实现方可参考行业中现有的相关协议进行对接。无论采用何种底层协议，商户侧返回的商品目录数据需满足以下要求，以确保买方智能体能够正确执行后续的规则检验与购物车确认流程：

- 返回的商品或服务明细中，应结构化地包含全局或局部唯一的商品标识、商品类目信息、明确的标价及货币单位；
- 宜携带商品价格的有效截止时间和库存状态反馈，避免智能体基于过期数据发起无效交易。

> 目前行业中已有若干相关协议对此进行了规范，例如：
>
> - UCP（Universal Commerce Protocol），由 Google 公司推出；
> - ACP（Agent Commerce Protocol），由 OpenAI 联合 Stripe 推出；
> - MCP（Model Context Protocol），由 Anthropic 公司推出。

### 5.2 CID-INT-XFR：意图上下文传递

#### 5.2.1 概述

意图上下文传递（Intent Routing）规范了买方智能体将委托人的意图上下文（Intent Context）传递至商户或平台电商，并获取候选商品/服务列表的请求/响应交互过程。买方智能体与商户之间需建立有效的意图上下文传递机制，使商户能够精准理解委托人的真实意图并据此完成商品筛选与推荐，并返回符合要求的候选列表供买方智能体进行展示或比较决策。

#### 5.2.2 意图上下文的多维度信息构成

为了让商户精准理解并推荐，买方智能体向商户传递的意图上下文宜包含以下多维度信息：

- **显式意图需求**：委托人通过自然语言等方式明确表述的购买需求（如"我想买一台轻薄笔记本"）；
- **隐式意图需求**：买方智能体基于与委托人的对话上下文逻辑，推断出的深层需求（如基于上下文对话，推断出"续航时间长"、"便携性高"等商品特点）；
- **约束条件**：基于委托人确认的意图中提取的刚性边界，如资金上限、允许的商品类目、指定商户白名单、配送时效等。
- **个人偏好信息**：买方智能体基于委托人历史交互记录提取的脱敏偏好描述（如：偏好特定品牌等）。

**结构化传递**：意图上下文中的显式/隐式意图、约束条件及偏好信息，可基于 `ADD-INT-ICS`（意图结构化表达规则）规范中定义的数据字段进行表达和传递。

> 注：隐式意图需求与个人偏好信息的传递均为可选，且须以委托人知情同意为前提。本协议不规定具体的同意机制，实现方应依据适用的数据保护法律法规自行处理。

#### 5.2.3 意图上下文传递的请求报文

买方智能体向商户或电商平台发起意图请求时，应构建包含完整意图上下文的请求报文，以便商户精准理解用户需求并进行安全校验。为了保障跨域流转的安全性与可追溯性，请求报文的核心信息应包含以下关键要素：

- **请求标识**：为防范重放攻击，每次请求应生成全局唯一的请求标识。在多轮交互的动态更新请求中，应通过关联历史请求标识来维持上下文的业务连贯性。
- **意图标识**：应包括 `intent_id`，在同一意图生命周期内保持不变，用于跨域链路追踪。
- **委托标识**：委托支付场景下宜包括 `delegation_id`，即时支付场景下可省略；
- **多维度意图信息**：买方智能体对本次购买意图的结构化描述，包含用户明确表达的显式意图、智能体推断的隐式需求以及经脱敏处理的用户偏好标签。
- **刚性商业约束**：买方智能体基于委托人确认的意图中提取的刚性边界，包括金额上限、品类范围等。
- **响应格式要求（可选）**：买方智能体对商户返回结果的格式或内容要求，如候选数量上限、推荐排序偏好等。
- **请求来源认证机制（可选）**：为防止意图请求被恶意第三方伪造，买方智能体宜对请求报文的关键要素和时间戳进行密码学签名，并附带自身的智能体身份标识，以便商户侧校验请求来源的真实性。

#### 5.2.4 意图上下文的动态更新

买方智能体应支持意图上下文的动态更新机制，以便在与委托人的多轮交互中，将补充的新信息实时融合并向商户发起重新查询。

动态更新请求应遵循以下要求：

- 请求链路连贯性：每次动态更新应生成新的请求标识（以防范重放攻击），并通过上一次请求的标识关联追踪链路。
- 增量传递原则：动态更新请求宜仅携带本次发生变化的意图内容，未发生变化的部分可省略，以降低商户侧的处理负担。

#### 5.2.5 商户返回的商品候选与多商户路由

商户或电商平台在接收到买方智能体的意图请求后，执行内部的匹配与筛选计算，并向买方智能体返回候选结果。该响应流程与关键要素应满足以下要求：

- **响应关联与商户身份**：商户的响应报文中应回传对应的请求追踪标识，供买方智能体确认响应与请求的对应关系，并携带商户自身的身份标识。
- **候选商品与服务明细**：商户应返回结构化的候选推荐列表。为满足买方智能体后续的规则自检要求，每条候选明细中：
  - 应包含商品标识、商品名称、明确的标价及货币单位、当前库存或可售状态；
  - 宜包括所属商品品类、价格的有效时间戳，预计的配送或履约时效；
  - 可包括商户侧引用地址等补充信息。
- **异常与错误处理**：当商户因库存不足、请求格式错误或无法满足约束条件而无法返回候选商品时，应返回错误响应，并告知买方智能体具体的错误类型及原因，以便智能体决定是更换商户还是通知用户。错误类型宜覆盖以下语义类别：
  - 格式错误：商户无法解析本次请求的内容或格式；
  - 无匹配结果：本次请求的约束条件下无可返回的候选商品或服务；
  - 访问受限：买方智能体不具备访问本商户接口的权限；
  - 约束冲突：请求中的约束条件存在内部矛盾，无法执行匹配；
  - 请求过频：买方智能体的请求频率超出商户的处理能力限制。

**多商户并发路由与比较决策**：在实际商业网络中，买方智能体可同时向多个不同的商户或电商平台并发发送请求。在汇总各方返回的候选列表后，买方智能体会依据委托人设定的意图边界与偏好，在本地自主完成跨平台的综合比价与最终购买决策。

**【存证】**决策完成后，买方智能体**宜**异步上报对应的 `act:commerce:decision-logged` 可信存证事件，记录最终选择了哪个商户的哪款商品以及决策摘要。

### 5.3 CID-CART-CFM：购物车确认

#### 5.3.1 概述

购物车确认（Cart Confirmation）规范了买方智能体在正式进入支付流程前，对本次购买意向进行最终确认的流程，以及在确认前执行的规则前置检验要求。

#### 5.3.2 规则前置检验

在正式向商户提交购物车并获取订单号之前，买方智能体应依据当前有效的用户意图结构化规则（ISR），对本次即将提交的购买行为执行规则自动校验。

买方智能体应完成以下维度的规则前置检验：

- **资金限额检验**
  - 单笔金额校验：本次拟购买总金额应不超过 IAC 中设定的单笔金额上限（若委托人已设置该上限）；
  - 累计额度校验：本次拟购买总金额与当前已累计消耗额度之和应不超过 ISR 中设定的累计授权总额上限。
- **品类范围检验**（若 ISR 中已设置品类约束时触发）：校验拟购买商品所属类目是否在委托人设定的品类允许范围之内，以及是否触发了禁止品类约束；
- **商户范围检验**（若 ISR 中已设置商户约束时触发）：核实提供本次商品或服务的目标商户，是否在委托人设定的允许商户范围之内；
- **履约时效检验**（若 ISR 中已设置履约时效要求时触发）：比对商户返回的预计配送或履约时间，是否满足委托人设定的最低时效要求；
- **价格变动容差检验**（若 ISR 中已设置价格变动容差时触发）：校验当前拟确认的最终价格，是否超出委托人设定的参考价格变动容差范围，以防止因商户动态调价导致的非预期资金损失。

检验未通过的处理机制：

- 若任一检验项未通过，买方智能体应依据 ISR 中预设的越界处理策略执行相应操作：
  - 若策略为**暂停并通知**：买方智能体应挂起当前流程，向委托人发送确认通知，等待委托人重新确认后方可继续；
  - 若策略为**自动取消**：买方智能体应终止本次商业交互，并记录取消原因。
- 若 ISR 未预设越界处理策略，买方智能体应默认采用**暂停并通知**策略。

#### 5.3.3 购物车确认流程与支付衔接

买方智能体在完成意图发现、比价决策并全部通过规则前置检验后，应与商户（或卖方智能体）完成订单级别的最终确认，为后续支付动作确立事实依据。步骤如下：

1. **提交锁定与订单生成**：买方智能体将所选定的商品/服务明细、最终协商价格及履约要求提交至商户（或卖方智能体）。商户在系统内锁定相关库存与价格，并生成全局唯一的订单交易号，并返回给买方智能体。商户应在锁定期内保持库存与价格有效，以确保买方智能体有足够时间完成后续支付执行。
2. **计算购物车快照**：买方智能体在收到商户侧订单交易号后，可将本次确认的购买标的（含商品或服务明细、各项价格、商户标识、商户侧订单交易号、关联的委托标识、意图标识、确认时间戳及实际总金额）序列化后计算数字摘要，形成不可篡改的购物车快照。
3. **【存证】**买方智能体宜异步上报 `act:commerce:cart-confirmed` 存证事件。
4. **发起支付执行准备**：购物车确认阶段至此完成，买方智能体已具备发起支付交易的前置条件，包括持有商户侧订单交易号、本次支付总金额及币种、确定的支付方式及对应支付服务方信息（可通过 `CID-PCA-NEG` 支付能力协商规范确认）以及委托人有效签发的意图授权凭证（用于委托支付场景）。

### 5.4 CID-PCA-NEG：支付能力协商

#### 5.4.1 概述

支付能力协商（Payment Capability Negotiation）规范了在 A2A 商业服务交互模式下，买方智能体与卖方智能体在发起正式支付前，对支付方式与 PSP 服务端点进行对齐确认的交互过程。

由于智能体生态中存在多种支付方式，买卖双方可能是动态发现与协商的，因此在支付能力上也需要一个标准化的能力发现与协商机制，以确保后续选定的支付方式及支付载荷能够被双方智能体及其背后的 PSP 所支持和正确解析。

本组件定义了两种协商模式（单向声明模式和双向协商模式），实现方宜支持单向声明模式，并根据业务复杂度可选支持双向协商模式。

#### 5.4.2 支付能力声明

卖方智能体可通过标准化路径对外公开其支付能力声明，包括在其 Agent Card 中包含支付能力声明字段，并在其域名的约定地址发布其支付能力声明文件（`.well-known/act-payment-capability.json`）。

Agent Card 中可通过 `capabilities` 节点声明本方支持的协商模式及对应的接口地址：

支持单向声明模式的 Agent Card 示例：

```json
{
  "agent_id": "did:act:example.com/agent-alice-001",
  "capabilities": {
    "act:payment:negotiation": {
      "mode": "one-way",
      "capability_url": "https://merchant.example.com/.well-known/act-payment-capability.json"
    }
  }
}
```

支持双向协商模式的 Agent Card 示例：

```json
{
  "agent_id": "did:act:example.com/premiumbot-02",
  "capabilities": {
    "act:payment:negotiation": {
      "mode": "two-way",
      "negotiation_endpoint": "https://api.example.com/act/payment/negotiate"
    }
  }
}
```

#### 5.4.3 单向声明模式

单向声明模式适用于卖方智能体已通过 Agent Card 完整公开其支付能力，买方智能体可直接读取而无需额外协商交互的场景。

流程如下：买方智能体通过 HTTP GET 请求获取卖方智能体 Agent Card 中声明的 `capability_url`，并读取支付能力文件，直接从 `supported_methods` 中筛选出与 IAC `allowed_payment_methods` 字段交集的可用方法，并获取对应的 `psp_id`、`endpoint` 及 `method_schema_url`，进入支付载荷构造流程。

该模式无需额外的协商请求，属于零往返的能力发现方式，适用于标准化程度较高的商业服务场景。

支付能力文件（`act-payment-capability.json`）的格式示例如下：

```json
{
  "version": "1.0",
  "role": "payee",
  "agent_id": "did:act:example.com/servicebot-01",
  "supported_methods": [
    {
      "method_id": "urn:act:payment:example-wallet",
      "psps": [
        {
          "psp_id": "urn:act:psp:example-psp",
          "endpoint": "https://api.example-psp.com/act-psp/v1",
          "method_schema_url": "https://specs.actprotocol.org/schemas/payment-payload.json"
        }
      ]
    }
  ]
}
```

#### 5.4.4 双向协商模式

双向协商模式适用于卖方智能体需要根据买方的具体请求上下文（如商品品类、预估金额、货币单位等）动态匹配支付方式的场景。

流程如下：

**第一步（买方发起）**：买方智能体向卖方智能体声明的 `negotiation_endpoint` 发送 HTTP POST 请求，请求体包含买方支持的支付方式列表、意图品类、货币及预估金额：

```json
{
  "agent_id": "did:act:example.com/agent-alice-001",
  "supported_methods": ["urn:act:payment:example-wallet", "urn:act:payment:credit_card"],
  "amount_currency": "CNY",
  "estimated_amount": 500.00
}
```

**第二步（卖方响应）**：卖方智能体返回匹配的支付方式及对应的 PSP 信息：

```json
{
  "matched_methods": [
    {
      "method_id": "urn:act:payment:example-wallet",
      "psp_id": "urn:act:psp:example-psp",
      "endpoint": "https://api.example-psp.com/act-psp/v1",
      "method_schema_url": "https://specs.actprotocol.org/schemas/payment-payload.json"
    }
  ]
}
```

若响应中 `matched_methods` 为空，则表示双方无可用的共同支付方式，本次交易无法继续，买方智能体应中止流程并向委托人反馈。

#### 5.4.5 协商结果

支付能力协商的最终输出为一组确定的 `method_id` + `psp_id` + `endpoint` + `method_schema_url`，这四项参数将用于后续 A2A 支付载荷构造的输入。

## 6 本域涉及的存证事件定义

本域可在以下节点触发存证事件，由智能体/商户或其代理存证服务商向信任服务域构建的联盟链（ACT Trust Chain）异步上报：

| 事件类型标识 | 触发时机 |
|-------------|---------|
| `act:commerce:decision-logged` | 买方智能体完成多候选比较决策，选定购买标的后 |
| `act:commerce:cart-confirmed` | 购物车确认完成，订单交易号生成后 |
| `act:commerce:fulfillment-completed` | 商户侧完成商品/服务的实际交付后，由商户上报 |
