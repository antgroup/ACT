# 目标与原则

> 状态：Draft / Non-normative

## 1. 问题陈述

当前项目同时呈现协议规范、产品概念、场景示例和模拟代码，但它们之间缺少稳定边界。开发者进入仓库后难以快速回答：

- ACT 解决什么问题？
- 哪部分是跨产品协议，哪部分是支付宝产品接入要求？
- 现有代码是演示、Quickstart，还是可用于真实接入的参考实现？
- 如何只接入 Agent 支付或 AI 按量付费？
- “接入 ACT 即接入支付宝 AI 付”具体需要满足哪些条件？

协议本身正在修订，因此当前阶段不适合通过修改组件编号、消息字段或 Schema 来解决上述问题。重构首先解决信息结构和开发者旅程，协议内容在修订完成后按明确门槛进入。

## 2. 产品目标

本轮开源重构的目标是：

> 开发者能够理解 ACT 的核心语义，选择支付宝 AI 付 Profile，并按照公开文档和可运行 Quickstart 接入支付宝产品。

“接入协议即接入产品”不表示 ACT Core 绑定支付宝字段，而表示仓库提供一条经过验证的组合路径：

```text
ACT Core
  + Alipay AI Pay Profile
  + Supported Transport/Binding
  + Product onboarding and credentials
  + Conformance tests
  = A verifiable Alipay AI Pay integration
```

## 3. 首期范围

### 3.1 Agent 支付

面向买方 Agent 和 Agent 开发者，覆盖公开可用的：

- AI 钱包开通、授权、绑定及状态检查。
- 支付意图展示和用户确认。
- 支付宝收银台链接支付。
- HTTP 402 支付。
- 支付状态查询和原任务恢复。

### 3.2 AI 按量付费

面向 API、MCP Tool 或 Skill 服务提供方，覆盖：

- 收费服务注册和产品开通指引。
- HTTP 402 支付要求。
- 支付凭证接收与验证。
- 金额、订单、资源与防重放校验。
- 资源交付和履约确认。
- 沙箱测试、错误恢复和上线检查。

### 3.3 暂不纳入首期承诺

- 尚未公开的 Agent Platform SDK 或智能硬件 SDK。
- 没有公开技术规范支撑的原生 MCP 支付 Transport。
- 长期额度授权、完全自主支付等 L2/L3 能力。
- 多支付渠道互操作实现。
- 未经真实产品或沙箱验证的“完整参考实现”声明。

这些能力可以在架构上预留扩展点，但不能阻塞首期闭环。

## 4. 分层原则

### 4.1 ACT Core

描述支付交互的中立语义，包括角色、消息含义、生命周期、安全约束和错误恢复。Core 不出现支付宝商户号、支付宝 API 名称、RSA2 等产品实现细节。

### 4.2 Product Profile

描述某一支付产品如何实现 ACT 语义。支付宝 AI 付 Profile 可以定义：

- `Payment-Needed` 和 `Payment-Proof` 的承载方式。
- 支付宝字段与 ACT 语义的映射。
- RSA2 签名规则。
- 支付验证和履约确认 API。
- AI 钱包及官方 Payment Skill 的接入路径。
- 支付宝产品状态、错误码和 ACT 恢复动作的映射。

### 4.3 Transport / Binding

描述消息如何被包装和传递，例如 HTTP Header、Skill 命令、MCP Tool 或 OpenAPI。不同 Transport 可以共享 Core 消息语义和验证规则。

### 4.4 Developer Assets

资产按可信程度分为：

| 类型 | 目的 | 是否证明真实接入 |
|---|---|---|
| Scenario | 解释业务角色和流程 | 否 |
| Demo | 展示交互体验，可使用模拟依赖 | 否 |
| Quickstart | 最短路径接入真实产品或官方沙箱 | 是 |
| Reference Implementation | 展示完整、可测试的协议实现 | 是，需声明覆盖范围 |
| Conformance Suite | 判断实现是否满足 Core/Profile | 是 |

## 5. 设计原则

1. **开发者旅程优先**：首页先帮助选择接入路径，再引导阅读协议细节。
2. **产品事实可追溯**：支付宝 Profile 的每项要求都应能追溯到公开资料或官方开源实现。
3. **协议与产品解耦**：Core 保持中立，Profile 保证产品可接入。
4. **不抢跑协议修订**：未决对象、字段和组件编号使用工作名称并进入追踪表。
5. **可运行胜过伪完整**：不能连接真实产品或沙箱的代码明确标记为 Demo。
6. **错误也是协议的一部分**：超时、重试、幂等、防重放和下一步动作必须进入设计。
7. **渐进交付**：先跑通 Agent 买方与按量付费卖方闭环，再扩展授权等级和更多 Transport。
8. **公开可复现**：开源用户不依赖内部文档、内部环境或隐含知识完成接入。

## 6. 成功标准

首期重构完成后，一位首次接触 ACT 的开发者应当能够在公开资料支持下：

1. 在 10 分钟内判断自己属于 Agent 开发者还是收费服务提供方。
2. 说明 ACT Core 与支付宝 AI 付 Profile 的边界。
3. 找到唯一、可执行的接入 Quickstart。
4. 在支付宝公开沙箱或官方公开能力上完成端到端支付、验证和履约。
5. 通过自动化检查判断实现是否符合对应 Profile。
6. 区分 Demo、Quickstart、参考实现和正式规范。
