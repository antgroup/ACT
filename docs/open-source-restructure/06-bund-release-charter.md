# 2026 外滩大会发布章程

> 状态：Accepted / Non-normative  
> 目标活动：[2026 Inclusion·外滩大会](https://www.inclusionconf.com/)  
> 大会日期：2026-09-09—12  
> 目标发布日期：2026-09-04  
> 最后更新：2026-07-15

## 1. 发布目标

大会前完成 ACT 开源仓库与支付宝 AI 付官网中以下两个公开产品的对齐：

1. Agent 支付。
2. AI 按量付费。

开发者应当能够从 ACT 仓库理解协议语义和产品关系，选择正确接入路径，并跳转到支付宝官网完成开户、沙箱和产品接入。ACT 不复制官网已经维护的产品操作手册，而是提供：

- ACT Core 与产品 Profile 的边界。
- ACT 语义到支付宝字段、API、Skill/CLI 和状态的映射。
- Agent 支付与 AI 按量付费的端到端关系。
- 使用官网公开方案和官方沙箱得到的验证证据。
- 与发布版本匹配的一致性检查。

## 2. 发布版本

大会版本采用：

```text
ACT Core 2.1 Draft / Release Candidate
+ Alipay AI Pay Profile 0.9 Preview
+ Agent Payment public integration guide
+ Metered Payment public integration guide
+ HTTP 402 end-to-end validation
```

在协议治理完成正式发布前，不使用 `Stable` 或“生产标准已经完成”等表述。

## 3. 公开接入基线

### 3.1 Agent 支付

首期以支付宝官网公开的 Skill/CLI 为唯一接入基线：

- 官方安装方式和钱包指引由支付宝官网维护。
- ACT 仓库解释钱包授权、支付意图、支付执行、结果查询与 ACT 语义的关系。
- Agent Platform SDK、智能硬件 SDK 和其他接入形式不进入大会版本承诺，后续通过新增 Binding 演进。

### 3.2 AI 按量付费

首期采用支付宝官网公开的 HTTP 402 流程：

```text
Resource Request
  → HTTP 402 + Payment-Needed
  → Agent Payment
  → Retry + Payment-Proof
  → Payment Verification
  → Resource Delivery
  → Fulfillment Confirmation
```

大会前不另行设计一套与官网竞争的支付流程。MCP Tool 和 Skill 是收费资源形态，可复用 402 闭环；如果未来出现公开的原生接入形式，再增加对应 Binding。

### 3.3 沙箱与产品文档

- 使用支付宝 AI 付官网已经提供的沙箱、接入方案和 API 文档。
- ACT 仓库通过稳定链接引用官网，不复制整段开户和沙箱教程。
- ACT 仓库只保留完成协议解释和映射所需的最小产品摘要。
- 发布前必须在官网沙箱完成验证，不能以模拟支付结果代替。

## 4. July Preview 定义

7 月初版截止时间为 2026-07-31，应至少包含：

### 4.1 开源入口

- 根 README 明确协议正在修订。
- 提供 Agent 开发者、收费服务提供方和协议实现者三条入口。
- 明确 Demo、Quickstart、Reference Implementation 和正式规范的区别。
- 移除或标记会误导接入的成熟度声明。

### 4.2 两条产品路径

- Agent 支付公开接入路径初版。
- AI 按量付费公开接入路径初版。
- 解释两者在 HTTP 402 闭环中的买方侧与卖方侧关系。
- 所有开户、沙箱和产品操作链接到支付宝官网。

### 4.3 Profile 骨架

- Alipay AI Pay Profile 的目录和版本状态。
- ACT 工作语义与支付宝产品实现的映射表。
- `Payment-Needed`、`Payment-Proof`、支付验证和履约确认的归属边界。
- Skill/CLI Binding 与 HTTP 402 Binding 的骨架。
- 产品待确认问题和协议依赖清单。

### 4.4 工程可信度

- 完成仓库断链、缺失文件、错误命令和虚假目录审计。
- 现有模拟 Demo 明确标记为非真实接入。
- 建立最小文档和代码检查入口。
- 形成 8 月工作项和负责人列表。

July Preview 不要求 ACT Core 修订正式定稿，也不要求复制或重新实现支付宝沙箱。

## 7. 双语范围

大会前采用：

- 中文覆盖全部大会版本文档。
- 英文覆盖根 README、架构摘要、两条 Getting Started 和 Profile 摘要。
- 详细 API、开户和沙箱步骤继续引用支付宝官网现有内容。
- 完整双语协议正文不作为大会版本的阻断项。

## 8. 官网单向对齐机制

支付宝官网不能由本项目同步修改，因此采用单向对齐：

1. 官网和支付宝官方开源仓库是产品事实源。
2. ACT Core 是协议语义源。
3. Alipay AI Pay Profile 负责两者之间的映射。
4. 每周检查官网文档标题、URL、字段、API 和流程是否变化。
5. 8 月 28 日记录大会版本使用的官网资料快照日期。
6. 官网变化导致 Profile 不再准确时，作为阻断或补丁问题处理。

ACT 文档不复制官网大段内容，从而降低两套文档漂移风险。

## 9. 发布门槛

大会版本只有同时满足以下条件才能发布：

### 9.1 协议与 Profile

- Core 与 Alipay Profile 边界经过评审。
- 大会所需的最小支付语义不存在未说明的冲突。
- 每项支付宝产品要求有公开官方来源。
- 未决问题明确标记，不伪装成确定结论。

### 9.2 开发者体验

- 开发者能在 10 分钟内选择正确接入路径。
- Agent 支付和 AI 按量付费都有唯一入口。
- 官网已有内容使用链接引用，没有重复维护的长篇教程。
- 新增本地链接、命令和代码检查通过。

### 9.3 产品验证

- 使用官网公开 Skill/CLI 完成 Agent 支付路径验证。
- 使用官网 HTTP 402 方案完成 AI 按量付费验证。
- 使用支付宝官网沙箱验证支付、凭证、验款和履约闭环。
- 不使用硬编码成功响应或模拟凭证作为发布证据。

### 9.4 安全与发布

- 仓库不包含测试或生产私钥、访问令牌和完整支付凭证。
- 凭证重放、重复履约、金额不一致和资源不一致有明确处理。
- 8 月 28 日后只接受阻断、安全和严重文档问题。
- 发布说明明确 Draft/Preview 状态及兼容范围。

## 10. 当前非阻塞开放项

以下问题需要在 7 月执行中确认，但不阻塞工作启动：

1. 首个验证采用哪个支持官方 Skill/CLI 的 Agent 运行时。
2. 官网沙箱是否覆盖 Agent 钱包与 402 卖方的同一端到端链路；若分为两段验证，发布证据如何组合。
3. 协议修订在 8 月 7 日前可冻结的最小对象集合。
4. 支付宝产品字段歧义的公开确认方式。

这些问题进入[修订追踪表](05-revision-tracker.md)，由对应负责人在里程碑验收前关闭或形成明确降级方案。
