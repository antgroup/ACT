# 场景三：商户视角 - 自主委托 A2A 支付

## 场景描述

作为商户，我通过卖方智能体（Merchant Agent）与平台 Agent 进行 A2A 交互，在 HTTP 402 语义扩展框架下发起支付诉求，接收支付凭证后提供履约服务。

## 角色定位

- **我是**：卖方商户，通过卖方智能体（Merchant Agent）参与 A2A 交互
- **我的客户**：自主委托任务中的买方智能体（平台 Agent）
- **服务对象**：需要完成复杂任务子项的终端用户

## 我的职责

1. **服务市场注册**：
   - 在服务市场中注册我的服务能力（如机票预订、酒店预订、用车服务等）
   - 发布支付能力声明（Payment Capability Declaration）
   - 支持 `CID-PCA-NEG` 支付能力协商

2. **参与支付能力协商**：
   - 接收买方智能体的支付能力查询请求
   - 声明支持的支付方式、PSP 端点、支付标记类型等
   - 与买方智能体匹配共同支持的支付方式

3. **生成支付诉求**：
   - 在完成商品/服务确认后，向买方智能体返回 HTTP 402 支付诉求响应
   - 支付诉求包含：金额、币种、商户标识、订单信息、期望的支付方法等

4. **接收支付凭证**：
   - 接收买方智能体通过 A2A 协议发送的支付凭证
   - 验证凭证的有效性和完整性
   - 向 PSP 验证支付凭证的真实性

5. **履约与资源交付**：
   - 支付验证通过后立即履约（出票、预订、交付等）
   - 向买方智能体返回包含支付回执的履约确认
   - 支持资源访问凭证的传递（如登机牌、酒店预订号等）

6. **支持支付挑战-响应**：
   - 遵循 `PSD-PAY-AUP` 的 A2A 通用支付协议骨架
   - 支持"支付挑战-凭证传递-履约回执"的标准交互流程

## 我的收益

- 接入 A2A 生态，被多个买方智能体发现和调用
- 自主定价和营销策略，保持商业独立性
- 通过标准化协议降低与不同平台对接的成本

## 技术要求

- 实现支持 HTTP 402 语义扩展的 API 端点
- 实现 `CID-PCA-NEG` 支付能力协商接口
- 支持支付凭证的解析和向 PSP 的验证
- 履约回执需包含支付凭证引用，确保可追溯

## 安全要求

- 不存储买方智能体的敏感身份凭证
- 支付凭证验证必须通过 PSP 完成
- 履约前必须确保支付凭证已通过验证
- 支持存证事件的生成与上报（可选但推荐）

## 互操作性

- 与买方智能体的通信基于 A2A 协议
- 支付环节补充 ACT 协议的身份认证与支付结算能力
- 通过标准化接口实现跨平台的智能体间协作

## 参考实现

- 作为卖方智能体参与平台 Agent 的出差任务：
  - 机票卖方智能体：提供航班查询、预订、出票服务
  - 酒店卖方智能体：提供酒店搜索、预订服务
  - 用车卖方智能体：提供接送机用车预订服务
