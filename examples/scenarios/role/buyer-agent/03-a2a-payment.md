# 场景三：通用买方智能体视角 - A2A 支付

## 场景描述

作为买方智能体，我在 A2A（Agent-to-Agent）生态中与其他智能体协作，基于 HTTP 402 语义扩展完成智能体间的支付，支持复杂任务的自动化执行。

## 角色定位

- **我是**：通用买方智能体（Buyer Agent），A2A 交互中的购买方代理
- **我的用户**：设定任务目标和预算的委托人
- **交互对象**：卖方智能体（Seller Agent）或其他服务提供智能体
- **核心能力**：A2A 通信、任务拆解、支付协商、自主决策

## 我的核心职责

### 1. 任务拆解与规划
将用户的复杂任务目标拆解为可独立执行的子任务：
- **任务分析**：理解目标的整体结构和依赖关系
- **子任务生成**：将复杂目标分解为最小可执行单元
- **依赖排序**：确定子任务执行顺序（并行/串行）
- **预算分配**：为各子任务分配合适的预算额度

### 2. 服务发现与卖方智能体寻址
- 在 A2A 服务市场中发现候选卖方智能体
- 基于能力声明、评价、历史记录筛选合适卖方
- 获取卖方智能体的 A2A 通信端点

### 3. 支付能力协商（`CID-PCA-NEG`）
在发起交易前与卖方智能体完成支付能力协商：
- 交互双方的支付能力声明（支持的支付方式、PSP、结算周期）
- 匹配共同支持的支付方式
- 确定支付参数（币种、结算时间、手续费承担方等）
- 记录协商结果用于后续支付流程

### 4. HTTP 402 支付诉求处理
- 接收卖方智能体返回的 HTTP 402 Payment Required 响应
- 解析支付诉求中的金额、收款方、订单信息、支付方法偏好
- 验证支付诉求的完整性

### 5. A2A 支付请求构造（`PSD-PAY-A2A`）
构造标准 A2A 支付载荷：
```json
{
  "iac": "<IAC凭证引用或JWT>",
  "sub_account": "<专属子账户标识（如适用）>",
  "payment_claim": {
    "amount": "<金额>",
    "currency": "<币种>",
    "merchant": "<卖方智能体身份>",
    "order_id": "<订单ID>"
  },
  "buyer_agent_signature": "<买方智能体签名>"
}
```

### 6. 支付凭证传递与履约监控
- 向卖方智能体发送支付请求并传递凭证
- 等待支付结果与履约确认
- 跟踪履约进度，处理履约延迟或失败

### 7. 多轮交易协调
在复杂任务中循环执行：
- 监控已执行子任务的预算消耗
- 基于剩余预算动态调整后续子任务策略
- 协调多个子任务间的依赖关系

### 8. 结果汇总与用户反馈
- 所有子任务完成后向用户汇总完整报告
- 包含各子项的交易记录、履约状态、预算使用情况
- 收集用户对各卖方智能体的评价

## A2A 支付流程详解

```
┌─────────────────┐
│ 买方智能体      │
└───────┬─────────┘
        │ 1. 发现卖方，启动A2A任务协商
        ▼
┌─────────────────┐      2. 能力交换
│   卖方智能体    │◄─────────────────►
└───────┬─────────┘
        │ 3. 确认商品/服务，返回HTTP 402
        │    (支付诉求)
        ▼
┌─────────────────┐      4. 构造A2A支付载荷
│   买方智能体    │
└───────┬─────────┘
        │ 5. 提交至PSP
        ▼
┌─────────────────┐      6. 核验IAC/子账户/预算
│      PSP        │
└───────┬─────────┘
        │ 7. 扣款，返回支付凭证
        ▼
┌─────────────────┐      8. 传递支付凭证
│   买方智能体    │
└───────┬─────────┘
        │ 9. 向卖方展示凭证，请求履约
        ▼
┌─────────────────┐      10. 验证凭证，提供资源/服务
│   卖方智能体    │
└───────┬─────────┘
        │ 11. 返回履约回执
        ▼
┌─────────────────┐
│   买方智能体    │      (多轮循环直至任务完成)
└─────────────────┘
```

## 不同 A2A 场景下的支付模式

### 模式1：即时 A2A 支付
- 买方智能体在场，确认后即时支付
- 可能仍需唤起用户确认（高金额场景）
- 支付凭证即时生成和传递

### 模式2：委托 A2A 支付（本场景重点）
- 基于 IAC 授权的无确认支付
- 使用专属子账户进行资金隔离
- 总预算管控下的多笔交易

### 模式3：担保 A2A 支付
- 资金先冻结，履约后释放
- 适用于需要确认履约的场景
- 支持争议时的资金划拨

## 与 HTTP 402 语义扩展的关系

ACT 协议使用 HTTP 402 Payment Required 语义扩展传递支付诉求：

```
HTTP/1.1 402 Payment Required
Content-Type: application/json

{
  "payment_claim": {
    "amount": "299.00",
    "currency": "CNY",
    "merchant_did": "did:act:seller001",
    "order_id": "ORD-2024-001",
    "description": "经济舱机票 北京-上海",
    "expiry": "2024-01-15T10:00:00Z",
    "supported_methods": [
      {"network": "cn.alipay", "priority": 1},
      {"network": "cn.wechat", "priority": 2}
    ]
  }
}
```

## 不同形态买方智能体的 A2A 差异

| 能力 | 平台型买方智能体 | 专属型买方智能体 |
|------|-----------------|-----------------|
| 卖方发现 | 大平台服务市场整合 | 需接入第三方市场或协议发现 |
| 身份呈现 | 平台身份背书 | 专属 DID 独立身份 |
| 决策模式 | 平台规则 + 用户偏好 | 深度个性化学习 |
| 资金管理 | 平台子账户或垫资 | 用户控制下的专属子账户 |
| 争议处理 | 平台兜底机制 | TSD 争议处理 + 用户自主 |

## 技术要求

- 实现 A2A 协议的智能体发现与调用接口
- 实现 `CID-PCA-NEG` 支付能力协商
- 实现 HTTP 402 语义扩展的解析与构造
- 支持 `PSD-PAY-A2A` 支付流程
- 支持支付凭证的生成、验证、传递
- 与 TSD 对接支持存证与争议处理

## 安全与信任

- 与卖方智能体建立双向身份认证（基于 `did:act`）
- 支付前验证卖方的服务声明和历史信誉
- 大额或首次交易时通过存证服务记录交易意图
- 支持交易撤销和争议提交机制

## 存证与争议职责

- 每笔 A2A 交易生成存证事件上报 TSD
- 保留支付凭证用于后续验证或争议
- 为用户代理争议提交和证据提供
